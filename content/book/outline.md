**가제**: 『에이전트 시대의 AI 보안 — 플랫폼 엔지니어를 위한 통제 설계』

이 초안은 2026-10-20 기준 수집 항목 20건과 두 축으로 만든 출발점이다. 장 제목·논지·순서는 저자가 고치고, 각 장 아래 "근거 항목"은 항목의 축 태그에서 자동으로 모인다(근거가 3건 미만이면 "근거 부족"으로 표시). 스케줄 작업은 이 문서를 고치지 않는다.

모든 장은 같은 틀로 쓴다: **리더용 요약 1쪽**(위험·발생 시 비용·내릴 결정) → 사례 → 동작 원리 → 통제 설계 → 점검 목록.

---

## 1부. 왜 AI 보안은 인프라 문제인가

### 1장. 프롬프트 인젝션은 고칠 버그가 아니라 상시 위험이다

- **논지**: 명령과 데이터가 한 채널을 쓰는 한 인젝션은 없어지지 않는다. 그래서 질문은 "막을 수 있나"가 아니라 "조작된 모델이 무엇에 닿을 수 있나(폭발 반경)"가 된다.
- **핵심 질문**: 공격 성공률이 낮다는 평가는 무엇을 숨기나? 프롬프트 안의 방어는 왜 통제가 아닌가?

{{< evidence ids="AISEC-2026-0005 AISEC-2026-0020 AISEC-2026-0004 AISEC-2026-0002" >}}

### 2장. 공격자도 에이전트를 쓴다

- **논지**: 성공률이 10%여도 시도 비용이 0에 가까우면 공격은 규모의 게임이 된다. 방어 쪽 패치·노출 관리 주기의 전제가 바뀐다.
- **핵심 질문**: 자율 침투 도구가 바꾼 공격 경제학, 노출된 관리 패널·업로드 엔드포인트의 의미

## 2부. 생명주기로 보는 공격 표면

### 3장. 데이터 — 학습·RAG에 들어가는 것들

- **논지**: 데이터 레이크와 수집 파이프라인은 "옛 유출을 한곳에 모으는 집적지"가 되기 쉽다.

{{< evidence lifecycle="data" >}}

### 4장. 학습·튜닝 — 평가와 정렬의 빈틈

- **논지**: 학습·평가 중의 에이전트도 실제 권한을 가진 행위자다. 채점기가 잡지 못한 행동은 몇 달 뒤에야 드러난다.

{{< evidence lifecycle="training" >}}

### 5장. 서빙·추론 — 모델 API와 애플리케이션

- **논지**: API 키 남용·증류·탈옥은 "모델 엔드포인트도 과금되는 공개 서비스"라는 사실에서 출발한다. 추론 최적화 옵션도 보안 변수다.

{{< evidence lifecycle="serving" >}}

### 6장. 에이전트 런타임 — 모델이 도구에 닿는 순간

- **논지**: 사고의 대부분은 모델이 파일·네트워크·자격 증명에 닿는 지점에서 난다. 미리보기·설정 필드 같은 부가 기능도 실행 경로다.

{{< evidence lifecycle="agent-runtime" >}}

### 7장. 공급망·배포 — 모델·MCP 서버·서드파티 플랫폼

- **논지**: 모델은 가중치가 아니라 "로더와 README가 딸린 패키지"다. MCP 서버 등록은 관리자 권한 부여와 같다.

{{< evidence lifecycle="supply-chain" >}}

## 3부. 통제 계층으로 막는다

### 8장. 신원·권한 — 에이전트에게 무엇을 쥐여 주는가

- **논지**: 에이전트의 의도가 아니라 닿을 수 있는 것으로 통제한다. 워크로드 ID 분리, 단기 토큰, 권한 부여 지점의 맥락 검증.

{{< evidence controls="identity" >}}

### 9장. 네트워크·egress — 나가는 길을 막는다

- **논지**: 유출 체인의 마지막 단계는 언제나 외부 호출이다. egress 허용 목록은 인젝션을 막지 못해도 피해를 막는다.

{{< evidence controls="network" >}}

### 10장. 격리·실행 환경 — 계획과 실행을 떼어 놓는다

- **논지**: 신뢰할 수 없는 입력은 자격 증명이 없는 곳에서 처리한다. 샌드박스, devcontainer, 렌더링 격리, 계획-실행 분리.

{{< evidence controls="isolation" >}}

### 11장. 공급망·출처 — SBOM에서 AI-BOM으로

- **논지**: 어떤 모델·패키지·MCP 서버가 어디서 왔는지 모르면 조달 배제 명령 하나에도 대응할 수 없다.

{{< evidence controls="provenance" >}}

### 12장. 탐지·평가 — 공격 성공률 너머를 본다

- **논지**: 행동 순서 기반 탐지, 실패 유형까지 보는 레드팀 지표, 모델·프롬프트 변경 때마다 재평가.

{{< evidence controls="detection" >}}

## 4부. 운영과 거버넌스

### 13장. 거버넌스·정책 — 리스크 등록부, 표준, 규제

- **논지**: 인젝션을 "열린 결함"이 아니라 담당자·범위·재평가 조건이 있는 상시 위험으로 등록한다. OWASP·NIST·규제 요건을 플랫폼 통제로 번역한다.

{{< evidence controls="governance" >}}

### 14장. 사고 대응과 레드팀 운영

- **논지**: 에이전트 사고의 포렌식은 "에이전트가 스스로 한 요약"이 아니라 해석된 인자까지 남긴 도구 호출 로그로 한다.

{{< evidence lifecycle="agent-runtime" controls="detection" >}}
