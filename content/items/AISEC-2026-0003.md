## 요약
공식 MCP Python SDK(PyPI `mcp`)의 HTTP OAuth 클라이언트가, 연결한 MCP 서버가 알려주는 인가 서버 정보를 충분히 검증하지 않았다. 악의적이거나 침해된 MCP 서버는 클라이언트를 자기가 고른 토큰 엔드포인트로 보내 클라이언트 시크릿·인가 코드·PKCE code verifier(PrivateKeyJWT 방식이면 서명된 client assertion)를 받아낼 수 있었고, 공격자는 이것으로 진짜 인가 서버에서 앱 권한의 유효 토큰을 얻는다. 2026-09-28 GHSA-qx49-fqc8-xw99로 공개됐고 1.30.0·2.2.0에서 수정됐다. CVSS 7.5(무인 M2M 프로바이더)/6.5(대화형)이며, CVE는 없고 실제 악용 보고도 없다. 수정 자체는 9월 7일 릴리스에 '동작 변경'으로 먼저 들어가 있었다.

## 동작 원리
OAuth 클라이언트가 "로그인은 어디서 하나"를 MCP 서버에게 묻고 그 대답을 그대로 믿은 구조다. 1.x는 issuer 검증도, 저장된 자격 증명과 인가 서버의 연결(바인딩)도 없었고, 2.x는 서버가 보호 리소스 메타데이터를 내지 않는 fallback 경로나 403 step-up 경로에서만 검사가 빠졌다. Cycode는 이 fallback 경로에서 issuer 검사가 아예 돌지 않고, 바인딩 검사는 공격자가 피해자의 진짜 issuer 이름을 적어 넣는 것만으로 통과한다는 점을 보였다. 대화형 흐름에서도 사용자가 보는 것은 진짜 로그인 페이지라 수상한 점이 없고, PKCE verifier까지 함께 넘어가므로 "코드를 훔쳐도 못 쓴다"는 PKCE의 안전장치도 무력해진다. 비유하면, 낯선 사람이 "수령 창구는 저쪽"이라고 하자 열쇠와 인감을 함께 그쪽에 넘긴 셈이다. 수정판은 기대하는 issuer를 먼저 정해 두고 다르면 거부한다.

## 플랫폼 엔지니어 관점
- 에이전트·도구 컨테이너 이미지의 SBOM에서 `mcp` 1.9.1~1.29.1, 2.0.0~2.1.1을 찾아 1.30.0 / 2.2.0 이상으로 고정한다.
- `ClientCredentialsOAuthProvider`·`PrivateKeyJWTOAuthProvider`는 업그레이드만으로 안 닫힌다. CI에 `issuer=` 누락을 잡는 정적 검사 규칙을 넣고, 1.30.0의 경고는 기본으로 숨겨지므로 테스트를 `-W error::DeprecationWarning`으로 돌려 드러낸다. `RFC7523OAuthClientProvider`는 교체 대상이다.
- 업그레이드 직후 저장된 OAuth 클라이언트 등록을 한 번 비우고, 신뢰할 수 없는 MCP 서버에 붙었을 수 있는 클라이언트는 시크릿 회전과 토큰 폐기를 한다.
- 근본 대책은 에이전트가 붙을 수 있는 MCP 서버를 허용 목록(egress 정책·MCP 게이트웨이)으로 제한하고, M2M 자격 증명을 MCP 클라이언트별로 분리해 한 서버의 배신이 다른 권한으로 번지지 않게 하는 것이다.
- 이번처럼 보안 수정이 "동작 변경"으로 먼저 릴리스되는 경우가 있으니, 핵심 SDK는 GHSA뿐 아니라 릴리스 노트도 구독한다.
