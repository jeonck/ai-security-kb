## 요약
Microsoft 연구진과 ISTA·CISPA 공동 저자들이 브라우저 에이전트용 정보 흐름 제어 방어 SPIDES를 공개했다. 웹 페이지 요소마다 '누가 써도 믿을 만한가(무결성)'와 '누가 읽어도 되는가(기밀성)' 레이블을 달고, 에이전트가 입력·클릭·페이지 이동을 할 때 그 레이블로 허용 여부를 정한다. 28개 사이트로 만든 벤치마크 MicroNet에서 5개 모델 모두 공격 성공률 0%를 냈다. 동일 출처 정책을 되살린 방어에는 절반 이상의 공격이 통했다. 대가로 정상 과제 완수율은 67~86%였고, 과제당 평균 1.84회의 사용자 승인이 필요했다. 사이트 운영자가 레이블을 달아야 한다는 점이 가장 큰 배포 장벽이다.

## 동작 원리
보안 검색대에 비유할 수 있다. 모델이 지시를 알아채기를 기대하는 대신, 비신뢰 텍스트와 기밀 데이터는 봉투에 넣어 에이전트에게 보여 주지 않는다. 에이전트가 봉투를 열면 그때부터 '오염된 상태'로 표시되고, 오염된 상태에서는 중대한 행동이나 외부 전송이 정책으로 막힌다. 방어 판단이 모델 출력이 아니라 레이블과 정책에서 나오기 때문에, 저자들은 모델이 완전히 공격자 편이 되어도 보장이 유지된다고 주장한다. 동일 출처 정책이 부족한 이유도 여기서 나온다. 같은 신뢰 사이트 안의 사용자 게시물이나 서드파티 iframe에도 공격 텍스트가 들어올 수 있기 때문이다.

## 플랫폼 엔지니어 관점
- 사내 브라우저 에이전트(업무 포털·위키·티켓 시스템 자동화)를 운영한다면, 사내 웹 앱은 우리가 운영자이므로 요소 단위 레이블을 달 수 있는 위치에 있다. 사용자 생성 콘텐츠 영역(댓글·티켓 본문)을 비신뢰로 표시하는 것부터 시작할 수 있다.
- 에이전트 하네스에서 코드 실행 도구를 끄고, 외부 전송(폼 제출·이동)은 허용 출처 목록으로 묶는다. 이 논문의 정책 구조(중대한 행동 정책과 외부 전송 정책의 분리)는 에이전트 게이트웨이 정책을 설계할 때 그대로 참고할 만하다.
- 방어를 평가할 때는 지시 인젝션뿐 아니라 데이터 인젝션(가짜 값 주입)도 따로 잰다. 이 논문에서 UCM은 지시 인젝션은 모두 막았지만 데이터 인젝션에는 43~63%가 뚫렸다.
- 승인 횟수도 지표로 둔다. 안전한 방어일수록 승인 요청이 늘고, 승인 피로는 다시 위험이 된다.
