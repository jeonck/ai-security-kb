## 요약
10월 21일 LLM 공급자 게이트웨이 라이브러리 LiteLLM의 1.107.0 휠 7종이 PyPI에 올라갔는데, 그 안에 Python이 시작될 때마다 실행되는 자격 증명 수집기와 원격 코드 로더가 들어 있었다. 같은 페이로드가 공식 GHCR·Docker Hub 이미지에도 실렸고 latest 등 떠다니는 태그가 몇 시간 동안 감염 이미지를 가리켰다. 빌드 출처 증명을 보면 릴리스는 정상 저장소가 아닌 하이픈 하나 다른 유사 저장소 Berri-AI/litellm에서 빌드됐다. Socket 스캐너가 게시 7분 만에 탐지했고 약 1시간 40분 뒤 PyPI에서 제거됐지만, 3월(1.82.7·1.82.8)에 이어 올해 두 번째 LiteLLM 침해다. 릴리스 워크플로가 어떻게 유사 저장소를 소스로 받아들였는지는 아직 밝혀지지 않았다.

## 동작 원리
Python은 시작할 때 site-packages의 .pth 파일과 sitecustomize.py를 자동으로 읽는다. 공격자는 이 '시동 스크립트' 자리에 파일 세 개를 심어, 라이브러리를 실제로 쓰지 않아도 그 가상환경에서 아무 Python이나 돌리면 수집기가 실행되게 했다. 진입은 코드가 아니라 포장지였다. 정상 코드 위에 빌드 설정 한 줄(data = cook)과 Dockerfile 한 줄을 얹은 유사 저장소를 릴리스 파이프라인이 소스로 집어 갔다. git 태그는 깨끗했고 커밋에는 Verified 배지까지 붙어 있어, 태그만 검토하거나 서명 배지만 보면 놓친다. 결국 출처 증명이 '이 빌드는 Berri-AI에서 왔다'고 정직하게 적어 두었는데도 그 값을 확인하는 사람이나 정책이 없었다.

## 플랫폼 엔지니어 관점
- 락파일·이미지 다이제스트·빌드 로그·캐시에서 litellm==1.107.0과 감염 이미지 다이제스트를 찾는다. 감염 환경에서는 python·pip로 점검하지 말고(재실행됨) 외부 도구로 보고, 호스트·파드를 격리한 뒤 클린 이미지로 재배포한다.
- LiteLLM 프록시가 닿던 모든 자격 증명(공급자 API 키, 클라우드 역할, 프록시 DB에 저장된 키, Kubernetes 서비스 계정 토큰)을 깨끗한 환경에서 회전한다. 게이트웨이는 키가 모이는 곳이라 영향 범위를 넓게 잡는다.
- 이미지는 latest 같은 떠다니는 태그 대신 다이제스트로 고정하고, 어드미션 정책(Kyverno·Sigstore policy-controller 등)에서 SLSA provenance의 source repository가 허용 목록과 정확히 일치하는지 검사한다. 이번 건은 그 한 줄 검사로 막을 수 있었다.
- 휠 RECORD에 .pth·sitecustomize.py가 새로 생기면 경보하는 패키지 검사와, 새 버전을 며칠 뒤에 받는 쿨다운 정책을 사내 프록시 레지스트리에 둔다(AISEC-2026-0023). 제거 뒤에도 캐시본을 내주는 미러가 있었으므로 사내 미러의 격리 절차도 점검한다.
- egress에서 litellm.dev 같은 신규 등록 도메인 요청을 차단·탐지한다. 게이트웨이 파드는 공급자 API 도메인 외 egress를 막아 두면 유출 단계가 실패한다.
