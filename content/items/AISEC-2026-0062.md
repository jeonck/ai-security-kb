## 요약
LiteLLM 1.107.0 오염(AISEC-2026-0053)에 대해 BerriAI가 같은 날 저녁 공식 사고 보고를 냈다. 공격자는 개발자 GitHub CLI OAuth 토큰 3세트를 갖고 있었다. 조직 소유자의 토큰으로 릴리스 워크플로의 브랜치 보호를 무시하고 유사 저장소를 소스로 바꿨다. 두 번째 토큰으로 운영 승인 게이트를 통과했고, 게시 직후 세 번째 토큰으로 워크플로 실행 기록을 지웠다. BerriAI는 공개 노출돼 있던 내부 LiteLLM 배포에서 수상한 계정을 찾았다. 공격자가 그곳 로그에서 토큰을 얻은 것으로 보며, Claude Code가 응답 본문에 GitHub CLI 토큰을 담는 현상을 유입 경로로 지목했다. 최초 진입 경로는 아직 확인되지 않았다.

## 동작 원리
3월 사고 뒤 LiteLLM의 금고는 단단해졌다. 비공개 릴리스 저장소, Trusted Publisher, 서명, 불변 태그, 승인 게이트를 갖췄다. 그런데 금고 문을 여는 열쇠가 사람 손에 있었다. 엔지니어의 GitHub CLI 토큰은 그 사람이 할 수 있는 일을 모두 할 수 있다. 조직 소유자의 토큰이면 보호 규칙도 끌 수 있다. 서로 다른 사람의 토큰 두 개를 쥔 공격자에게는 ‘다른 사람이 승인한다’는 2인 통제도 의미가 없었다. 열쇠가 새어 나온 곳은 AI 게이트웨이 자신이었다. 코딩 에이전트가 오가는 요청·응답 본문을 프록시가 로그로 남겼고, 그 로그에 개발자 토큰이 섞였다. 게이트웨이 로그가 사내 개발자 자격 증명을 모으는 저장소가 된 셈이다. 그 로그가 있는 내부 배포가 인터넷에 열려 있었다.

## 플랫폼 엔지니어 관점
- 릴리스·승인 권한은 사람 CLI 토큰이 아니라 워크로드 ID(OIDC)에만 주고, 브랜치 보호 우회(bypass) 권한은 조직 소유자를 포함해 아무에게도 상시로 두지 않는다. 임시 권한 확대에는 만료 시각을 건다.
- 승인 게이트는 ‘다른 계정’이 아니라 ‘다른 사람·다른 기기’를 요구하도록 하드웨어 키·SSO 재인증을 붙인다. 워크플로 실행 기록 삭제 권한은 따로 떼고 감사 로그를 외부로 내보낸다.
- LLM 게이트웨이·에이전트 프록시의 요청·응답 본문 로깅은 기본 끄거나 비밀 마스킹(gh 토큰 ghu_/gho_ 접두어 등)을 적용하고, 로그 저장소를 자격 증명 저장소와 같은 등급으로 접근 통제한다. 내부 관리 배포가 인터넷에 노출돼 있는지 점검한다.
- 개발자 GitHub CLI 토큰은 GitHub CLI의 단기 자동 갱신 토큰(AISEC-2026-0058)으로 바꾸고, 사고 대응 시 조직 전체 OAuth 앱 토큰을 일괄 회수할 절차를 준비한다.
- 1.107.0을 받은 환경은 블로그의 노출 시간창(PyPI 11:39~13:23, Docker Hub 11:46~14:20 UTC)으로 판정하고, 정리 전 pip를 실행하지 말고 이미지·가상환경을 처음부터 다시 만든다.
