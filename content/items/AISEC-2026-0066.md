## 요약
Nous Research의 Hermes Agent는 웹훅 경로마다 쓸 수 있는 도구 묶음(웹, 터미널, 파일 등)을 따로 정한다. 그런데 요청 인증은 URL의 경로 이름으로 하면서, 도구 권한은 세션 chat_id(‘webhook:경로:전달ID’)를 콜론으로 쪼개 얻은 이름으로 다시 찾았다. 그래서 ‘build:external’이라는 저권한 경로의 비밀만 가진 사람이 ‘build’ 경로의 터미널·파일 도구로 에이전트를 움직일 수 있었다. 수정은 9월 18일 병합됐고 CVE-2026-114463이 10월 21일 공개됐다.

## 동작 원리
출입증 검사와 권한 부여를 다른 직원이 하는 건물을 떠올리면 된다. 정문 경비는 ‘build:external(외부 협력사)’ 출입증을 정확히 확인하지만, 안쪽 직원은 명찰을 첫 콜론까지만 읽고 ‘build(내부 빌드팀)’로 알아듣고 서버실 열쇠를 건넨다. 요청은 정상적으로 서명돼 있어 겉보기엔 아무 이상이 없고, 권한 상승은 에이전트 내부에서 일어난다. 저권한 경로가 공개 GitHub 이슈처럼 누구나 내용을 쓸 수 있는 입력을 받는다면, 이슈 본문 속 프롬프트 인젝션이 곧바로 셸 명령 실행으로 이어진다.

## 플랫폼 엔지니어 관점
- Hermes Agent를 웹훅 게이트웨이로 운영한다면 PR #115285가 포함된 빌드로 올리고, 당장 못 올리면 경로 이름에서 콜론을 없앤다. 로그에서 콜론 경로 세션이 설정 밖 도구를 쓴 흔적을 찾는다.
- 에이전트 플랫폼 전반에서 ‘인증된 주체’를 문자열로 다시 조립·파싱하지 말고, 인증 단계가 만든 신뢰 메타데이터(세션 속성)로만 권한을 계산하는지 코드 리뷰 항목에 넣는다.
- 공개 입력(이슈·PR 댓글·외부 웹훅)을 받는 경로와 터미널·파일 도구가 있는 경로는 같은 프로세스·같은 자격 증명에 두지 않는다. 고권한 경로는 별도 파드·별도 서비스 계정으로 분리하면 이런 매핑 오류가 나도 폭발 반경이 줄어든다.
- 웹훅 HMAC 비밀은 경로별로 다르게 두고, 외부 협력사에 준 비밀이 새면 어떤 도구까지 닿는지 정기적으로 시험한다.
