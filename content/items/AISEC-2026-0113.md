## 요약
Google Cloud는 10월 22일 산호세 AGNTCon + MCPCon에서 AI 에이전트 전용 컴퓨트 서비스 Agent Compute Engine(ACE)과 거버넌스 기능 확장을 발표했다. 에이전트 세션마다 자체 커널을 가진 microVM을 주고, Titanium IPU와 하드웨어 가상화로 격리한다. 핵심은 자격 증명 처리 방식으로, 샌드박스 안에는 장기 비밀이 하나도 없고 외부 호출은 Agent Gateway가 사용자 위임·에이전트 신원·노드 증명을 확인한 뒤 실제 자격 증명을 전송 중에 끼워 넣는다. 쿠버네티스용 오픈소스 런타임 Agent Substrate는 GKE에서 바로 쓸 수 있고 관리형 ACE는 수개월 안에 프리뷰로 나온다.

## 동작 원리
은행 창구에 비유하면, 에이전트는 금고 열쇠 없이 신청서만 들고 창구(게이트웨이)에 가는 직원이다. 창구는 ‘이 고객이 이 직원에게 위임했는가’(OBO 부여), ‘이 직원이 진짜 그 샌드박스에서 왔는가’(단기 SPIFFE 신원), ‘그 샌드박스가 검증된 하드웨어 위에 있는가’(Titanium 노드 증명)를 확인한 다음, egress·DLP 정책을 통과하면 그제서야 진짜 열쇠(장기 토큰)를 붙여 백엔드로 보낸다. 게스트 VM에는 네트워크 인터페이스도 메타데이터 서버 접근도 없고, 모든 트래픽은 vsock을 거쳐 밖의 프록시로만 나간다. 그래서 프롬프트 인젝션이 에이전트를 장악해 루트까지 얻어도 빼 갈 비밀이 없다. 다만 Google 설명도 인정하듯 인젝션은 여전히 모델 행동을 바꿀 수 있으므로, 에이전트가 원래 허가받은 범위 안의 행동을 악용하는 것까지 막지는 못한다.

## 플랫폼 엔지니어 관점
- 자체 에이전트 플랫폼에서도 같은 패턴을 적용할 수 있다: 에이전트 파드에서 서비스 계정 토큰 자동 마운트·메타데이터 서버 접근을 끊고, 자격 증명은 사이드카가 아닌 노드 밖 egress 프록시에서 주입한다.
- 에이전트 신원은 SPIFFE/SPIRE 같은 단기 워크로드 신원으로 주고, 프록시는 ‘사용자 위임 + 워크로드 신원 + 노드 증명’을 모두 확인한 요청에만 토큰을 붙이도록 정책을 짠다.
- 컨테이너 격리 대신 gVisor·Kata·Firecracker 계열 microVM 런타임클래스를 에이전트 실행에 쓰는지 검토한다(Agent Substrate가 GKE에서 gVisor/microVM을 쓰는 구조 참고).
- 남는 위험(허가 범위 안의 오용)에 대비해 게이트웨이 단계에서 도구 호출별 정책·DLP·로깅을 따로 설계한다. 벤치마크 수치는 Google 자체 측정이므로 도입 전 자체 부하 시험이 필요하다.
