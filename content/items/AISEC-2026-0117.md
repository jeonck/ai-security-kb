## 요약
AI가 찾아낸 PHP 코어 원격 코드 실행 취약점 PHP2Shell이 공개된 다음 날, 개인정보보호위원회가 개인정보처리자에게 유출 예방조치를 당부했다. 과기정통부·KISA의 패치 안내에 더해, 개인정보위는 침해 이후 DB가 털리는 단계를 막는 데 초점을 맞췄다. DB 관리 도구의 인터넷 직접 접근 차단, 웹 서비스 계정의 DB 권한 최소화, 대량 조회·내보내기 탐지, 수탁사·호스팅 환경 점검이 핵심이다. 정부 부처 대응(AISEC-2026-0102)과 별개로 개인정보 감독 기관이 움직였다는 점에서 이 사건의 규제 파장이 넓어지고 있음을 보여 준다.

## 동작 원리
PHP2Shell은 인증 없이 웹 서버에서 명령을 실행하게 한다. 공격자가 웹 서버를 쥐면 그다음은 웹 애플리케이션이 가진 DB 계정과 접속 정보로 개인정보를 대량으로 빼 가는 단계다. 개인정보위의 권고는 이 두 번째 단계를 끊는 것이다. 웹 계정이 필요한 테이블만 읽게 하면 털리는 범위가 줄고, phpMyAdmin을 인터넷에서 치우면 손쉬운 우회로가 사라지며, 평소와 다른 대량 조회를 보면 유출을 진행 중에 잡을 수 있다. 패치가 정문을 잠그는 일이라면 이 조치들은 금고를 따로 잠그고 경보기를 다는 일이다.

## 플랫폼 엔지니어 관점
- Kubernetes에서 PHP 워크로드가 쓰는 DB 자격 증명을 점검한다. 애플리케이션 계정이 스키마 전체 권한(DDL·전체 SELECT)을 가졌다면 읽기 범위를 테이블·열 단위로 줄인다.
- phpMyAdmin·Adminer 같은 관리 도구를 Ingress로 노출하지 않는다. 필요하면 내부망 전용 + 단기 자격 증명 + 접근 로깅으로만 연다.
- DB 감사 로그에서 단위 시간당 반환 행 수·내보내기 쿼리를 기준선 대비 경보로 건다. RAG·에이전트 파이프라인이 같은 DB를 읽는다면 그 계정도 같은 기준을 적용한다.
- 위탁 운영·외부 호스팅에 맡긴 시스템의 PHP 버전을 공급업체에 서면으로 확인받고, 계약상 패치 기한을 명시한다.
- 개정 개인정보 보호법의 ‘유출 가능성’ 통지 의무를 고려해, 침해 징후 발견 시 판단·통지 절차를 사고 대응 런북에 넣어 둔다.
