## 요약
LiteLLM 1.107.0 오염 사건(AISEC-2026-0053, AISEC-2026-0062)의 근본 원인이 정정됐다. LiteLLM은 10월 23일 공격 체인 분석을 내고, 첫 보고에서 추정한 ‘노출된 내부 배포의 로그’는 진입점이 아니었다고 밝혔다. 진짜 진입점은 실험용 내부 서비스 Agent Platform의 마스터 키였다. 이 키는 5월 27일 공개 저장소의 opencode.json에 커밋됐다가 덮였지만 회수되지 않았다. 공격자는 10월 10일 이 키로 에이전트 설정을 조회해 조직 소유자의 GitHub CLI 토큰을 얻었다. 이어 임시 브랜치 워크플로로 CI 비밀을 빼내 메인테이너 두 명의 토큰을 확보했고, 11일 뒤 그 토큰들로 릴리스를 유사 저장소로 돌려 승인·게시했다. 같은 날 Socket은 GitHub에 남은 10·12일 비밀 탈취 워크플로의 흔적을, Microsoft는 페이로드의 실행 체인과 복구 지침을 공개했다.

## 동작 원리
에이전트 플랫폼은 에이전트가 PR을 올릴 수 있도록 GitHub 토큰을 설정에 보관한다. 그런데 이 플랫폼에 넣어 둔 것은 전용 서비스 계정의 좁은 토큰이 아니라 조직 소유자 본인의 CLI 토큰이었다. 플랫폼의 마스터 키는 금고 열쇠 꾸러미를 여는 열쇠였던 셈이고, 그 열쇠가 다섯 달 동안 공개 저장소 이력에 남아 있었다. 소유자 권한을 얻은 공격자는 코드를 바꾸지 않았다. 짧게 쓰고 지우는 브랜치에 push 트리거 워크플로를 올려 CI가 가진 비밀을 밖으로 보내게 했다. 포크 PR과 달리 저장소 안의 push는 비밀에 닿는다. 이렇게 서로 다른 사람의 토큰을 모으자 ‘한 사람이 시작하고 다른 사람이 승인한다’는 2인 통제는 형식만 남았다. 서명·Trusted Publisher·승인 게이트는 모두 정상 작동했고, 정상 절차로 악성 빌드에 서명했다.

설치된 페이로드는 Python이 시작할 때 자동으로 읽는 .pth와 sitecustomize 자리에 숨었다. 그래서 LiteLLM을 import하지 않는 스크립트, 점검하려고 실행한 pip까지 수집기를 깨운다. 두 번째 장치는 GitHub의 평범한 텍스트 파일을 가리킴판으로 쓰는 원격 로더라, 지금 조용하다는 사실이 안전을 뜻하지 않는다.

## 플랫폼 엔지니어 관점
- 노출된 비밀은 커밋을 덮거나 강제 푸시하는 것으로 끝나지 않는다. 노출 탐지 즉시 회수하고, 회수 완료를 별도로 확인하는 티켓을 닫아야 사고가 종결되도록 절차를 바꾼다. 실험용·알파 내부 서비스의 키도 운영 키와 같은 회수 대상 목록에 넣는다.
- 에이전트 플랫폼·코딩 에이전트 하네스에 넣는 GitHub 자격 증명은 사람 토큰이 아니라 저장소 범위로 제한된 GitHub App 설치 토큰이나 전용 서비스 계정으로 한다. 에이전트 설정을 반환하는 API는 비밀을 마스킹해 돌려주게 한다.
- GitHub Actions에서 환경 비밀은 보호 브랜치 전용 environment로 묶고, 임의 브랜치 push로 도는 워크플로가 조직·환경 비밀을 읽지 못하게 한다. 짧게 생겼다 지워진 브랜치의 워크플로 실행, 실행 기록 삭제, 브랜치 보호 우회 이벤트를 조직 감사 로그에서 경보로 건다.
- 릴리스 승인 규칙을 완화할 때는 만료 시각과 하드웨어 키 재인증을 같이 건다. ‘다른 계정’이 아니라 ‘다른 사람·다른 기기’를 요구해야 토큰 두 개를 쥔 공격자를 막는다.
- 1.107.0이 돌았던 노드·파드·CI 러너에서는 python·pip를 실행하지 말고 파일 시스템을 떠서 깨끗한 도구로 site-packages의 .pth·sitecustomize.py를 확인한다. 이미지는 다이제스트로 고정해 재빌드하고, 패키지 승인 정책에 ‘휠에 .pth·sitecustomize.py가 새로 생기면 차단’ 규칙을 넣는다.
