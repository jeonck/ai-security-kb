## 요약
Obsidian 노트 볼트를 에이전트에 연결하는 MCP 서버 obsidian-tc의 권고 두 건이 2026-10-23 GitHub Advisory Database에 검토 등재됐다. 새로 CVE가 붙은 CVE-2026-115477은 사람 확인(HITL) 단계의 결함이다. 파괴적 도구를 실행하기 전 사람에게 묻는 구조였는데, 서버가 묻기 전에 만든 상태값을 ‘승인됨’의 증거로 받아들여, 사람이 거절해도 클라이언트가 그 값을 되돌려 보내면 삭제·이동이 실행됐다. 1.31.4에서 고쳤지만, 클라이언트가 스스로 ‘승인’ 응답을 만들어 내는 것은 프로토콜 구조상 서버가 막을 수 없다고 권고가 인정했다. 함께 등재된 CVE-2026-77363(CVSS 9.6)은 인증 없는 루프백 HTTP 전송에 Origin 검증이 없어 웹 페이지 방문만으로 볼트 전체 권한을 얻는 문제다.

## 동작 원리
확인 결함은 ‘결재 서류 양식을 받은 것’을 ‘결재 도장을 받은 것’으로 착각한 구조다. 서버는 확인 질문을 띄우기 전 호출에 묶인 서명된 상태값(requestState)을 클라이언트에 주고, 클라이언트는 사람의 답과 함께 그 값을 돌려보낸다. 서버는 값이 진짜인지만 확인하고 사람의 답이 ‘수락’인지는 보지 않았다. 패치 뒤에는 답이 수락이어야 하지만, 확인 화면을 띄우는 쪽이 클라이언트인 이상 악성 클라이언트는 사람에게 묻지 않고 ‘승인’이라고 답할 수 있다. 사람 확인이 실제 통제가 되려면 확인 화면과 결과를 신뢰할 수 있는 쪽이 소유해야 한다.

DNS 리바인딩 결함은 로컬 개발 서버 계열의 고전 문제다. 루프백에만 열려 있어도 브라우저는 악성 페이지의 요청을 127.0.0.1로 보낼 수 있고, 서버가 Origin·Host를 검사하지 않으면 그 요청은 로컬 사용자로 취급된다.

## 플랫폼 엔지니어 관점
- 에이전트 플랫폼의 ‘위험 도구 실행 전 사람 승인’은 승인 UI와 승인 기록을 클라이언트(모델 쪽 에이전트)가 아닌 플랫폼·게이트웨이가 소유하게 설계한다. 클라이언트가 보고하는 승인 결과만 믿는 구조는 감사 대상으로 표시한다.
- 파괴적 도구는 승인 여부와 별개로 스냅숏·되돌리기, 범위 제한(폴더·태그 단위 권한)을 둔다.
- 개발자 PC에서 도는 로컬 MCP 서버는 Streamable HTTP 대신 stdio를 기본으로 하고, HTTP가 필요하면 허용 Origin·Host 목록과 인증을 강제한다. 엔드포인트 관리 도구로 127.0.0.1 위의 무인증 MCP 포트를 점검한다.
- obsidian-tc를 쓰는 팀은 1.31.4 이상으로 올린다.
