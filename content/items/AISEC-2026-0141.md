## 요약
vLLM 프로젝트가 10월 초 저장소에 공개해 둔 보안 권고들에 VulnCheck가 CVE 10건을 붙여 10월 25일 일괄 게시했다. 가장 무거운 것은 CVE-2026-116176으로, 프리필과 디코드를 다른 노드에 나눠 돌리는 분리형 구성(P2pNcclConnector)에서 클라이언트가 X-Request-Id 헤더에 자기 서버 주소를 넣으면 프리필 워커가 그 주소로 연결해 KV 캐시 텐서를 넘긴다. KV 캐시에는 다른 사용자의 프롬프트 내용이 담기므로 사실상 추론 데이터 유출이다. 나머지는 범위 밖 토큰 ID, 압축 오디오 폭탄 등으로 엔진을 쓰러뜨리는 서비스 거부 결함들이며, 대부분 0.24.0~0.29.0에서 고쳐졌다.

## 동작 원리
분리형 추론에서는 프롬프트를 읽는 프리필 노드가 계산 결과(KV 캐시)를 생성 담당 디코드 노드로 GPU 통신(NCCL)으로 넘긴다. 이때 ‘누구에게 보낼지’를 요청 ID 문자열 안에 적어 두는 방식을 썼는데, 그 요청 ID를 클라이언트가 보낸 헤더에서 그대로 가져왔다. 택배 송장의 받는 사람 칸을 고객이 직접 적게 한 셈이다. 공격자가 자기 주소를 적으면 워커는 성실하게 공격자 서버와 통신 채널을 맺고 캐시를 보낸다. 서비스 거부 결함들은 공통적으로 ‘요청 값이 정수인지·파일인지만 보고 크기와 범위는 안 본다’는 문제로, GPU 커널이나 디코더까지 검증 없는 값이 내려가 프로세스 전체가 죽는다.

## 플랫폼 엔지니어 관점
- 버전: vLLM을 최소 0.29.0 이상(SSRF·오디오는 0.24.0, stop_token_ids는 0.29.0)으로 올리고, 이미지 태그를 고정해 어떤 클러스터가 어느 버전인지 인벤토리로 확인한다.
- 분리형 추론 egress: 프리필·디코드 워커 Pod에 NetworkPolicy로 상대 워커 CIDR만 허용하고 그 밖으로의 ZMQ·NCCL 연결을 막는다. 추론 워커는 외부로 나갈 이유가 없다.
- 헤더 정규화: 게이트웨이(Envoy·Ingress)에서 클라이언트의 X-Request-Id를 버리고 새 UUID로 덮어쓴다. 내부 라우팅 정보를 클라이언트 헤더에서 받지 않는 원칙을 점검한다.
- 인증: --api-key 없이 띄운 vLLM을 내부망이라고 방치하지 않는다. 앞단 게이트웨이에서 인증·테넌트별 쿼터를 강제한다.
- 가용성: 한 요청이 엔진을 죽일 수 있으므로 헬스 체크·자동 재시작·요청 단위 격리(테넌트별 엔진)와 입력 크기·멀티모달 길이 제한을 게이트웨이에 둔다.
