## 요약
Firecrawl은 웹 페이지를 LLM이 읽기 좋은 형태로 긁어 오는 서비스로, 에이전트의 웹 도구로 널리 쓰인다. 자바스크립트를 실행하는 Playwright 엔진은 내부 주소를 막는 SSRF 필터 프록시를 거치지만, 주소를 검사할 때와 실제로 연결할 때 DNS를 따로 조회했다. 공격자가 자기 도메인의 DNS 응답을 두 번 다르게 주면 필터를 통과한 뒤 사설망으로 연결된다. 10월 20일 이슈로 보고돼 다음 날 수정됐고, 10월 25일 CVE-2026-116066으로 게시됐다.

## 동작 원리
경비원이 방문객의 주소를 확인하고 들여보냈는데, 택시 기사는 주소를 다시 물어 다른 곳으로 가는 구조다. 첫 번째 질문(검사)에는 공인 주소, 두 번째 질문(연결)에는 169.254.x.x 같은 내부 주소를 답하는 DNS 서버만 있으면 된다. 스크레이퍼는 가져온 내용을 API 응답으로 돌려주므로, 내부망에서 본 화면이 그대로 공격자에게 돌아간다. 수정은 ‘검사한 주소로만 연결한다’는 원칙을 코드로 강제한 것이다.

## 플랫폼 엔지니어 관점
- 셀프 호스팅 Firecrawl은 수정 커밋(PR #5261) 이후 버전으로 올리고, Playwright 서비스 파드에 클라우드 메타데이터(169.254.169.254)·클러스터 내부 대역으로 가는 egress를 NetworkPolicy로 막는다. 애플리케이션 필터만 믿지 않는다.
- 에이전트에 붙인 웹 페치·스크래핑 도구(MCP 포함)는 연결 시점 주소 검증을 하는지, 아니면 별도 egress 프록시를 거치는지 점검한다. PROXY_SERVER를 쓰면 그 프록시가 내부 대역 차단을 맡아야 한다.
- IMDSv2(홉 제한 1)를 강제하고, 스크래핑 워커에는 클라우드 권한이 없는 서비스 계정을 붙인다.
