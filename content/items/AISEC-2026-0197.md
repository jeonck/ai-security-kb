## 요약
닷넷 CMS인 Umbraco가 AI 애드온의 권한·자격 증명 처리 문제를 한 권고(GHSA-xc89-5cg7-36xf)로 묶어 10월 27일 패치했다. 백오피스 사용자가 AI 에이전트에게 일을 시키면, 에이전트의 읽기 도구는 그 사용자가 볼 수 없는 초안과 회원 전용 페이지까지 읽었고, 쓰기 도구는 사용자에게 콘텐츠 섹션 권한이 있는지조차 확인하지 않았다. 관리자가 사용자 그룹별로 걸어 둔 도구 제한도 편집기 안 도구와 다른 환경으로 배포한 에이전트에는 적용되지 않았다. 여기에 Deploy 연동이 AI 제공자 API 키를 평문으로 배포 파일에 써서, 저장소를 읽을 수 있는 사람이면 키를 얻을 수 있었다. 점수는 6.5(Moderate)이고 인증이 필요하며 해당 도구는 기본 비활성이다.

## 동작 원리
에이전트 도구가 ‘누구를 대신해’ 움직이는지가 핵심이다. 사람이 화면에서 클릭하면 CMS는 그 사람의 권한을 검사하지만, 에이전트 도구는 내부 서비스 API를 바로 불러 권한 검사를 건너뛰었다. 결과적으로 에이전트는 요청자보다 넓은 권한을 가진 대리인이 됐고, 요청자는 에이전트에게 부탁하는 방식으로 자기 권한을 넘어섰다. 그룹별 도구 제한은 도구 이름 목록으로 걸려 있어서, 같은 기능이 ‘도구 그룹’이라는 다른 이름으로 들어오거나 설정이 다른 환경으로 복제될 때 빠졌다. 자격 증명 문제도 뿌리가 같다. 에이전트 설정을 코드처럼 배포하면서 그 안의 키를 비밀 저장소가 아닌 파일에 담았다.

## 플랫폼 엔지니어 관점
- Umbraco AI 애드온 다섯 패키지를 수정 버전으로 올린다. Umbraco Cloud도 AI 애드온은 자동으로 올라가지 않는다.
- Deploy 파일이 커밋된 저장소의 Git 이력에서 AI 제공자 키를 찾아 교체하고, 시크릿 스캔(푸시 보호)을 켠다. 모델 API 키는 환경별 비밀 저장소나 워크로드 신원으로 주입한다.
- 사내 에이전트 도구를 설계할 때 도구 호출은 반드시 호출한 사용자의 위임 토큰으로 백엔드 권한 검사를 거치게 한다. 에이전트 서비스 계정의 넓은 권한으로 대신 조회하지 않는다.
- 도구 허용·차단 정책은 도구 이름이 아니라 동작(읽기·쓰기·게시)과 리소스 단위로 정의하고, 환경 간 배포 후 정책이 그대로 적용되는지 회귀 테스트로 확인한다.
