## 요약
Yang 등은 웹 서비스가 AI 에이전트에게 MCP 도구로 백엔드 기능을 열었을 때, 기존 웹 취약점이 얼마나 그대로 악용되는지를 실행형 벤치마크 VELA로 측정했다. 12개 앱 계열의 취약점 44건 중 91%가 기준 MCP 인터페이스를 통해서도 그대로 악용 가능했다. Claude Code·Codex·Grok Build 중 무엇을 쓰든 결과 차이는 최대 4.5%p였고, 결과를 가른 것은 인터페이스를 엔드포인트형·워크플로형·자연어 질의형 중 어떻게 설계했느냐였다(유지율 39~95%). 다만 가장 안전해 보인 질의형은 정상 기능도 절반 넘게 잃었다.

## 동작 원리
에이전트용 도구는 기존 API 위에 얹은 얇은 포장지다. 포장지를 바꿔도 안쪽 백엔드의 SQL 처리·권한 검사·자원 처리 로직은 그대로라서, 공격자가 에이전트를 통해 같은 인자를 넣으면 같은 취약점이 터진다. 에이전트가 ‘중간에 있다’고 공격이 걸러지지 않는다. 오히려 에이전트는 공격자 요청을 성실히 도구 호출로 바꿔 주는 통역사 역할을 한다. 인터페이스를 좁히면(자연어 질의 하나만 받고 서버가 해석) 공격 경로도 줄지만, 같은 이유로 정상 업무도 함께 막힌다.

## 플랫폼 엔지니어 관점
- 사내 서비스에 에이전트용 MCP 서버를 붙일 때 기존 API와 같은 보안 테스트(DAST·인가 테스트)를 MCP 경로에도 그대로 돌린다. ‘에이전트 전용이라 내부용’이라는 예외를 두지 않는다.
- 사용자·테넌트 ID처럼 신원에 의존하는 인자는 도구 스키마에서 빼고, 게이트웨이가 세션 토큰에서 주입하게 한다.
- 객체 수준 인가(BOLA 방지)와 워크플로 순서 검사는 MCP 어댑터가 아니라 백엔드 서비스에서 모든 요청에 강제한다.
- 인터페이스를 좁히는 결정을 할 때는 공격 유지율뿐 아니라 정상 기능 커버리지도 함께 측정해 보고한다.
