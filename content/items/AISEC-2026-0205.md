## 요약
CaMeL은 프롬프트 인젝션을 모델 학습이나 탐지로 막는 대신 시스템 설계로 막으려는 방어다. 사용자 질의는 신뢰하고 이메일·문서·웹 결과 같은 도구 출력은 신뢰하지 않는다고 가정한다. 특권 LLM은 사용자 질의만 보고 할 일을 파이썬 코드로 쓰고, 격리 LLM은 도구 없이 비신뢰 데이터를 정해진 스키마로 파싱만 한다. 맞춤 인터프리터가 코드를 실행하면서 값마다 출처와 허용 독자를 붙이고, 도구 호출 직전에 보안 정책을 검사한다. AgentDojo에서 o3 High 기준 과제 77.3%를 풀어 무방어 84.5%와 큰 차이가 없었다. 다만 모델에 따라 효용 감소가 30%p를 넘기도 했고, 토큰 비용은 약 2.8배였다.

## 동작 원리
기존 Dual LLM 패턴은 ‘도구를 쥔 모델이 비신뢰 데이터를 보지 않게’ 하는 데서 멈춘다. 저자들은 이것만으로는 부족하다고 지적한다. ‘지난 회의에서 Bob이 요청한 문서를 보내라’는 지시의 순서는 지켜도, 회의록에 심긴 문구가 수신자 주소나 파일 이름을 바꾸면 기밀 문서는 엉뚱한 곳으로 간다. CaMeL은 운영체제의 capability와 정보 흐름 통제를 가져온다. 모든 값에 ‘어디서 왔고 누가 읽어도 되는가’ 꼬리표를 붙이고, 값이 계산을 거치면 꼬리표도 따라간다. ‘이메일 보내기’ 같은 도구를 부르기 직전에 정책 함수가 꼬리표를 보고 판단한다. 예를 들어 비신뢰 출처에서 온 주소로 비공개 문서를 보내는 호출은 거부된다. 모델이 속더라도 위험한 데이터 흐름이 생기지 않게 하는 것이 목표다. 저자들은 이를 제어 흐름 무결성(CFI)에 비유하면서도, CFI가 ROP로 우회됐듯 부채널과 데이터→제어 흐름 전환이 남는다고 인정한다.

## 플랫폼 엔지니어 관점
- 에이전트 플랫폼에서 ‘계획 모델’과 ‘비신뢰 데이터 파서’를 별도 워크로드(별도 Pod·ServiceAccount)로 나눈다. 파서 쪽에는 도구 자격 증명과 egress를 주지 않고, 출력은 JSON 스키마 검증을 통과한 구조화 값만 넘기게 한다.
- 도구 게이트웨이(MCP 프록시 등)에 호출 단위 정책 엔진(OPA 등)을 두고, 인자에 출처 메타데이터를 실어 보내게 한다. ‘수신자·URL·파일 경로가 비신뢰 출처에서 왔으면 외부 전송 거부’ 같은 규칙을 코드로 관리하고 CI에서 테스트한다.
- 도입 전에 효용·비용을 자체 측정한다. 논문에서 같은 설계라도 모델에 따라 효용 감소가 3%p~32%p로 달랐고 토큰은 약 2.8배 들었다. 모델 교체 때마다 AgentDojo 같은 벤치마크로 회귀 평가를 돌린다.
- 정책 거부가 잦으면 사용자가 승인을 남발한다(논문의 사용자 피로 문제). 거부 이벤트를 로그·지표로 남겨 정책을 다듬고, 승인 우회 횟수를 경보로 본다.
- CaMeL은 실험 단계의 연구 구현이다. 컨테이너 격리·자격 증명 분리·egress 차단을 대체하지 않고 그 위에 얹는 계층으로 다룬다.
