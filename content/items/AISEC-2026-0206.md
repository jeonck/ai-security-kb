## 요약
에이전트 보안 연구자와 업계 실무자 14명이 프롬프트 인젝션을 설계로 막는 패턴 여섯 가지를 정리한 논문이다. 출발점은 범용 에이전트에는 신뢰할 만한 보장을 주기 어렵고, 탐지·모델 개선 같은 휴리스틱은 깨지기 쉽다는 판단이다. 그래서 할 일이 정해진 용도 특화 에이전트를 대상으로, 비신뢰 입력을 읽은 뒤에는 중대한 행동을 못 하게 묶는 구조를 제안한다. 각 패턴의 보안 효과와 효용 손실을 비교하고, 이메일 비서·SQL 에이전트·코딩 에이전트 등 10개 사례에 적용해 본다. 결론은 한 패턴으로 모든 위협을 막을 수 없으니 여러 패턴을 조합하라는 것이다.

## 동작 원리
핵심은 ‘무엇을 할지 정하는 쪽’과 ‘비신뢰 데이터를 읽는 쪽’을 떼어 놓는 것이다. 식당에 비유하면 Action-Selector는 메뉴판에 있는 요리만 주문받는 점원이다. 손님 쪽지에 무엇이 적혀 있든 메뉴 밖의 일은 못 한다. Plan-Then-Execute는 장보기 목록을 먼저 확정한 뒤 시장에 가는 방식이라, 시장 전단지가 목록을 바꿀 수 없다. 다만 목록 안의 ‘누구에게 보낼지’ 같은 빈칸은 여전히 오염될 수 있다. Dual LLM은 비신뢰 문서를 읽는 직원에게 전화(도구)를 주지 않고, 결과는 봉투(기호 변수)에 담아 넘긴다. 결정권자는 봉투를 열지 않고 전달만 지시한다. Map-Reduce는 서류를 한 장씩 다른 직원에게 맡겨 오염을 한 장 안에 가두고, Context-Minimization은 결정이 끝난 뒤 원래 요청을 치워 응답에 끼어들지 못하게 한다. 어느 패턴이든 에이전트가 할 수 있는 일을 줄이는 대가로 보안을 얻는다.

## 플랫폼 엔지니어 관점
- 새 에이전트를 플랫폼에 올릴 때 ‘범용인가, 용도 특화인가’를 등록 항목으로 받고, 용도 특화 에이전트에는 허용 도구·행동 목록(Action-Selector식 템플릿 SQL·API)을 매니페스트로 고정한다. 매니페스트 밖 호출은 도구 게이트웨이가 거부한다.
- 이메일·티켓·웹 문서를 읽는 단계와 도구를 호출하는 단계를 분리된 워크로드로 운영한다. 읽는 쪽 ServiceAccount에는 시크릿·쓰기 권한·egress를 주지 않고, 출력은 스키마 검증된 값만 넘긴다.
- 계획 확정형(Plan-Then-Execute) 워크플로라면 계획을 실행 전에 로그로 남기고, 실행 중 계획 밖 도구 호출이 나오면 차단·경보한다. 수신자·URL 같은 인자는 별도 정책(허용 도메인·사내 주소록)으로 검사해 인자 조작의 빈틈을 메운다.
- 코딩 에이전트는 외부 문서·서드파티 코드를 그대로 컨텍스트에 넣지 말고, 격리된 단계에서 정형 API 요약으로 바꿔 넘기는 방식을 검토한다. 사용자 확인 창만으로는 숨은 import를 막기 어렵다는 논문의 평가를 근거로, 의존성 추가는 CI의 별도 검증(허용 레지스트리·잠금 파일 diff 검토)으로 막는다.
- 패턴 선택표(논문 Table 1)를 팀 설계 리뷰 체크리스트로 바꿔, 에이전트마다 어떤 패턴을 어떤 위협에 적용했는지 기록한다.
