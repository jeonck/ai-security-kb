## 요약
Google Cloud가 2026년 10월 27일 IAM Helper를 공개했다. 에이전트가 IAM 작업을 직접 다루게 하는 스킬 4종(정책 관리, 403 진단, 정책 시뮬레이터, PAM 기반 JIT 권한)과, Policy Troubleshooter·Analyzer·Simulator를 감싼 읽기 전용 IAM MCP 도구로 이뤄진다. 스킬은 Agent Skills 표준을 따르며 Gemini CLI뿐 아니라 Claude Code·Cursor에서도 쓸 수 있다. 정책 관리 스킬은 allUsers 공개나 owner·editor 같은 기본 역할 부여를 적용 전에 막는다. 진단·시뮬레이션은 자동으로 돌지만 실제 정책 변경은 위험 등급에 따라 사람 확인을 거친다.

## 동작 원리
코딩 에이전트가 배포하다 권한 오류(403)를 만나면 흔히 하는 해법은 사람이 서비스 계정에 넓은 역할을 붙여 주는 것이다. IAM Helper는 이 과정을 에이전트에게 맡기되 안전한 길로만 가게 한다. 에이전트는 먼저 읽기 전용 MCP 도구로 무엇이 빠졌는지(허용 바인딩인지, 상위 폴더의 거부 규칙인지) 찾는다. 그다음 영구 역할 대신 PAM에 1시간짜리 권한을 요청하거나, 최소 권한 정책을 만들어 지난 90일 로그에 대고 '이걸 적용하면 무엇이 깨지나'를 시뮬레이션한다. 실제 변경은 관리자 승인을 거친다. 비유하면 에이전트가 열쇠를 깎는 대신 출입 대장에 임시 출입을 신청하고 경비가 도장을 찍는 구조다.

## 플랫폼 엔지니어 관점
- 에이전트와 CI 파이프라인의 서비스 계정에 roles/editor 같은 넓은 역할이 붙어 있다면, 이런 JIT·시뮬레이션 흐름으로 갈아탈 대상부터 목록화한다. 403이 날 때 넓은 역할을 붙이는 관행을 막는 것이 핵심이다.
- 에이전트가 권한을 '요청'할 수 있게 되면, 요청자와 승인자가 같은 신원이 되지 않게 PAM 승인자 그룹에서 에이전트·파이프라인 ID를 빼고 자기 승인을 차단한다.
- 위험 등급(HITL 기준)을 기본값에 맡기지 말고 조직 정책으로 정한다. 예: 프로젝트 밖 범위, 거부 규칙 변경, 서비스 계정 키 관련 변경은 항상 사람 승인.
- 읽기 전용 MCP 도구라도 조직 전체의 IAM 구조를 에이전트에게 보여 준다. 이 정보도 정찰 자료가 되므로 MCP 호출을 감사 로그로 남기고 어떤 에이전트가 무엇을 조회했는지 본다.
- Kubernetes(Workload Identity)나 다른 클라우드도 같은 원칙(진단은 자동, 변경은 시간 제한·승인)으로 에이전트용 권한 요청 경로를 설계할 수 있다.
