## 요약
에이전트는 MCP 도구를 고를 때 도구 설명 텍스트를 본다. 그런데 설명은 실제로 어떤 구현이 실행되는지를 보증하지 않는다. ProbeID는 도구에 스키마에 맞는 탐침 질의를 보내고, 응답을 승인 시점에 저장한 기준 응답과 비교해 같은 도구인지 판정한다. 애매하면 판정을 보류한다. 사칭 도구 실험에서 hit@1 0.956을 보였고, 설명 기반 라우터는 우연 수준이었다. 실제 MCP 도구 59개를 11주 동안 추적한 결과 7개가 응답이 바뀌었고, 그중 3개는 버전 표기가 그대로였다.

## 동작 원리
이름표만 보고 사람을 들여보내면 이름표를 베낀 사칭자를 막을 수 없다. ProbeID는 이름표 대신 '면접 질문'을 던져 대답 방식이 등록 당시와 같은지 본다. 사칭자가 통과하려면 겉모습만이 아니라 탐침이 관찰하는 동작까지 똑같이 흉내 내야 한다. 다만 면접 질문이 닿지 않는 행동, 즉 응답을 바꾸지 않고 몰래 하는 외부 전송이나 부작용은 잡지 못한다. 실측은 또 다른 교훈을 준다. 의존성 범위가 넓게 선언돼 있으면 버전을 고정해도 재설치만으로 동작이 바뀐다.

## 플랫폼 엔지니어 관점
- MCP 서버 승인 시 도구 정의(이름·설명·스키마)의 해시만 저장하지 말고, 읽기 전용 도구에 대해서는 대표 질의의 기준 응답도 함께 저장해 정기 재검증에 쓴다.
- MCP 서버 이미지·패키지는 버전 번호가 아니라 잠금 파일과 다이제스트로 고정한다. 전이 의존성 범위가 넓으면 재빌드 때 동작이 바뀐다는 것이 실측으로 확인됐다.
- MCP 게이트웨이에서 같은 이름·비슷한 설명의 도구가 여러 서버에 등록되면 경보를 낸다(사칭 탐지의 1차 신호).
- 행동 검증은 응답에 드러나지 않는 유출을 못 잡으므로, MCP 서버 egress 제한과 함께 쓴다.
