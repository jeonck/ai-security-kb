## 요약
Model Context Protocol(MCP)의 공식 Python·TypeScript SDK 보안 권고 4건이 2026년 10월 27일 GitHub Advisory Database에 검토를 거쳐 한꺼번에 올라왔다. Python SDK 3건에는 CVE가 붙었다. 서버가 다른 서비스용으로 발급된 bearer 토큰을 받아 주는 문제(CVE-2026-116684), HTTP 클라이언트가 교차 출처 리다이렉트를 따라가며 커스텀 인증 헤더와 본문을 넘기는 문제(CVE-2026-116685), 도구 결과 검증 중에 서버가 지정한 `$ref` URL을 클라이언트가 직접 가져오는 SSRF·정지 문제(CVE-2026-116686)다. TypeScript SDK 1건은 HTTP 서버가 요청 크기와 JSON-RPC 배치 길이를 제한하지 않아 생기는 서비스 거부다(CVSS 7.5). 모두 수정판이 나왔지만, 토큰 audience 검사는 설정을 바꿔야만 켜진다.

## 동작 원리
- **audience 미검증**: 사내 인가 서버 하나가 여러 서비스용 토큰을 찍어 낸다면, A 서비스용 출입증으로 B 건물(MCP 서버)에도 들어갈 수 있었던 셈이다. SDK의 토큰 검증 인터페이스에는 ‘이 토큰이 누구를 위한 것인가’를 돌려주는 자리가 없었다.
- **리다이렉트 유출**: 클라이언트가 MCP 엔드포인트에 X-API-Key를 붙여 요청했는데, 그 엔드포인트가 만료된 도메인 등 다른 곳으로 리다이렉트되면 키가 그대로 따라갔다. Authorization 헤더는 HTTP 라이브러리가 지워 주지만, 커스텀 헤더는 그렇지 않았다.
- **$ref 원격 조회**: JSON Schema의 `$ref`는 ‘이 정의는 저 주소에 있다’는 포인터다. 서버가 도구 출력 스키마에 내부망 주소나 `file://` 경로를 넣으면, 결과를 검증하던 클라이언트가 그 주소를 직접 열었다. 응답 없는 주소를 넣으면 타임아웃 없이 이벤트 루프가 멈춘다.
- **요청 크기 무제한**: 큰 본문이나 매우 긴 배치 하나로 서버 메모리를 고갈시키거나 다른 클라이언트를 기다리게 만든다. `express.json()` 같은 본문 파서는 배치 길이를 막지 못한다.

## 플랫폼 엔지니어 관점
- 사내 에이전트·MCP 서버 이미지에서 `mcp`(pip)를 1.30.0/2.2.0 이상, `@modelcontextprotocol/sdk`를 1.30.1 이상(2.x 계열은 server·node 2.1.0, hono 2.0.1)으로 올리고, SBOM에서 고정 버전을 찾아 재빌드한다.
- MCP 서버가 공유 IdP 토큰을 받는다면 `validate_token_resource=True`와 `resource_server_url`을 반드시 켜고, `verify_token()`이 audience를 돌려주는지 통합 테스트로 확인한다(한쪽만 바꾸면 모든 요청이 401). 서비스별 audience를 분리 발급하도록 IdP 정책도 점검한다. 같은 날 AWS API MCP Server의 같은 유형 결함(AISEC-2026-0223)도 공개됐다.
- 리다이렉트를 따라갔을 가능성이 있는 클라이언트가 실어 보낸 API 키는 교체한다. MCP 엔드포인트 URL은 리다이렉트 없는 최종 주소로 고정한다.
- 신뢰하지 않는 서드파티 MCP 서버에 붙는 에이전트 파드에는 egress 허용 목록을 걸어 클라이언트 측 SSRF가 내부망·메타데이터 엔드포인트로 가지 못하게 한다.
- HTTP로 노출되는 MCP 서버 앞 인그레스·리버스 프록시에 본문 크기 제한을 둔다.
