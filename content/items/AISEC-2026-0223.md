## 요약
AWS가 공개한 오픈소스 MCP 서버 awslabs.aws-api-mcp-server는 AI 비서가 AWS CLI 명령을 대신 실행하게 해 준다. 1.3.0부터 1.5.x까지는 streamable-http 전송에 OAuth 인증을 켜면, 들어온 베어러 토큰의 서명·발급자·만료만 확인하고 토큰이 어느 앱을 위해 발급됐는지(audience/client id)는 보지 않았다. 그래서 같은 IdP 테넌트(예: 같은 Cognito 사용자 풀)의 다른 앱에 발급된 토큰을 가진 사람이 서버에 접근해, 서버 호스트에 설정된 AWS 자격 증명으로 API를 호출할 수 있었다. AWS는 2026-10-27 보안 공지 2026-152-AWS와 GHSA를 함께 냈고, 1.6.0에서 기대 audience나 client id 설정을 필수로 바꿨다.

## 동작 원리
회사 출입증 비유가 맞다. 출입증이 진짜인지(서명), 우리 회사가 발급했는지(발급자), 유효기간이 지났는지(만료)는 확인했지만, 그 출입증이 ‘이 건물’용인지는 보지 않은 셈이다. 같은 IdP에서 여러 앱이 토큰을 받는 환경에서는 다른 앱용 토큰도 서명·발급자·만료 검사를 모두 통과한다. MCP 인가 사양이 audience 바인딩을 요구하는 것도 이 때문이다. 이 서버가 쥔 것은 호스트의 AWS 자격 증명이므로, 토큰 검증 한 줄이 빠지면 그 IAM 권한 전체가 노출된다.

## 플랫폼 엔지니어 관점
- 사내에 aws-api-mcp-server를 HTTP로 띄웠다면 버전을 1.6.0 이상으로 올리고 AUTH_AUDIENCE(또는 Cognito라면 AUTH_CLIENT_ID)를 명시한다. 포크나 사내 파생본도 같은 수정을 적용한다.
- 자체 개발한 MCP 서버·게이트웨이의 토큰 검증 코드에서 aud·azp·client_id 검사가 있는지 점검한다. 같은 IdP 테넌트를 여러 앱이 공유하는 구조라면 이 결함이 그대로 재현된다.
- MCP 서버에 붙이는 AWS 자격 증명은 읽기 전용 등 최소 권한 역할로 분리하고, 파드 단위 IRSA/Pod Identity로 범위를 좁힌다. 토큰 검증이 뚫려도 피해 범위는 IAM 권한이 정한다.
- CloudTrail에서 MCP 서버 역할의 호출 주체·소스를 모니터링하고, 예상하지 않은 클라이언트의 호출을 탐지 규칙으로 만든다.
