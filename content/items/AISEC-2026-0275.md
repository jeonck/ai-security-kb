## 요약
원격 개발 환경(CDE) 플랫폼 Coder에서, GCP VM 위의 워크스페이스 에이전트가 Google 인스턴스 신원 토큰으로 자신을 증명하는 엔드포인트가 토큰의 수신자(audience)를 확인하지 않는 결함이 고쳐졌다. 같은 VM이 다른 서비스용으로 받은 유효한 신원 토큰을 누군가 손에 넣어 Coder에 내밀면, 그 워크스페이스 에이전트의 세션 토큰을 받아 다음 빌드 때까지 에이전트로 행세할 수 있었다. 저장소 권고는 10월 13일 나왔고, CVE-2026-118687이 10월 28일 NVD와 GitHub Advisory Database에 게시됐다.

## 동작 원리
GCE 신원 토큰은 Google이 서명한 ‘이 VM이 맞다’는 증명서이고, aud 클레임은 ‘이 증명서를 누구에게 내미는 것인가’를 적는 칸이다. Coder는 서명과 만료만 보고 이 칸을 보지 않았다. 다른 은행 창구에 내라고 발급된 신분 확인서를 들고 와도 받아 준 셈이다. 신원 토큰은 로그·프록시·제3자 서비스로 흘러가기 쉬운데, 그 한 시간짜리 토큰이 다음 빌드까지 유효한 장수명 에이전트 세션 토큰으로 ‘교환’되면서 피해 창이 길어졌다.

## 플랫폼 엔지니어 관점
- Coder를 GCP에서 운영하면 수정 버전으로 올리고, 템플릿이 GCP 인스턴스 신원 인증을 쓰는지 확인한다. 바로 못 올리면 auth = token으로 바꾸고 워크스페이스를 재시작해 에이전트 토큰을 새로 받는다.
- 워크스페이스 VM에서 메타데이터 서버 신원 토큰을 로그·트레이스에 남기는 코드나 프록시를 찾아 막고, 제3자 서비스에는 format=standard 토큰을 쓴다.
- 워크로드 신원 토큰을 받아 다른 자격 증명으로 바꿔 주는 모든 교환 지점(Kubernetes 프로젝트 서비스 계정 토큰, OIDC 연동, MCP 서버 OAuth)에 aud 검사가 있는지 점검 목록을 만든다. 같은 달 AWS API MCP Server와 MCP Python SDK에서도 같은 누락이 나왔다.
- 원격 개발 환경에서 AI 코딩 에이전트를 돌린다면 워크스페이스 에이전트 세션 토큰이 곧 그 에이전트의 신원이다. 토큰 수명을 빌드 주기와 분리해 짧게 하는 설정이 있는지 확인한다.
