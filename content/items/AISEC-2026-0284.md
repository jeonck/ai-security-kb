## 요약
Red Hat OpenShift AI와 Models-as-a-Service에 들어가는 ai-gateway-payload-processing 구성 요소에서 CVE-2026-117574가 공개됐다. 게이트웨이는 요청에 적힌 모델 ID를 보고 공유 저장소에서 해당 공급자 API 키를 꺼내 붙여 주는데, 그 모델이 요청자 테넌트의 것인지 확인하지 않았다. 그래서 로그인만 한 다른 테넌트 사용자가 남의 모델 ID를 적어 남의 키와 할당량으로 LLM을 호출할 수 있었다. CVSS 9.1, Red Hat 영향도 Important이며, 영향·수정 버전은 아직 공개되지 않았다.

## 동작 원리
AI 게이트웨이는 사용자가 OpenAI·Anthropic 같은 공급자 키를 직접 갖지 않게 하려고, 요청이 지나갈 때 키를 대신 꽂아 주는 ‘주입’ 방식을 쓴다. 이는 비밀을 사용자 손에서 떼어 놓는 좋은 설계지만, 무엇을 꽂을지 정하는 근거가 요청자가 마음대로 쓰는 필드(모델 ID)라면 문제가 된다. 호텔 프런트가 방 번호만 듣고 카드키를 내주는 것과 같다. 투숙객 신원과 방이 맞는지 보지 않으면 누구든 남의 방에 들어간다.

## 플랫폼 엔지니어 관점
- 다중 테넌트 AI 게이트웨이를 쓰는 팀은 자격 증명 선택이 ‘인증된 주체(테넌트·서비스 계정)’와 ‘모델 ID’를 함께 키로 쓰는지 확인한다. 요청 헤더·본문의 식별자만으로 키를 고르는 경로는 인가 정책(OPA·Authorino 등)으로 막는다.
- 수정판이 나오기 전까지는 테넌트별로 게이트웨이 인스턴스나 비밀 저장소 네임스페이스를 나눠 공유 저장소를 쓰지 않는 구성을 검토한다.
- 공급자 키마다 사용량 상한과 테넌트별 사용량 알림을 걸어, 다른 테넌트가 내 키로 호출할 때 비용·할당량 이상으로 드러나게 한다. 게이트웨이 로그에 ‘요청 주체 테넌트’와 ‘주입된 키 소유 테넌트’를 함께 남겨 불일치를 탐지한다.
- 에이전트 플랫폼에서도 같은 패턴(도구 호출 시 게이트웨이가 토큰을 대신 주입)을 쓴다면, 주입 대상 선택 로직을 동일한 기준으로 감사한다.
