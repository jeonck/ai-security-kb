## 요약
PDF를 읽어 주는 MCP 서버 @sylphx/pdf-reader-mcp는 HTTP 모드에서 API 키를 설정하면 ‘인증이 켜졌다’고 로그를 남겼지만, 실제로는 요청의 키 헤더를 확인하는 코드가 없었다. 기본으로 모든 네트워크 인터페이스에 바인딩됐기 때문에 같은 네트워크에서 포트에 닿기만 하면 누구나 PDF 도구를 호출해 서버가 접근할 수 있는 PDF를 읽을 수 있었다. URL 입력을 통한 제한적 SSRF도 가능했다. 3.0.1에서 키 검사, 루프백 기본 바인딩, 경고가 추가됐다.

## 동작 원리
현관에 ‘보안 시스템 작동 중’ 스티커만 붙이고 경보기는 연결하지 않은 셈이다. 운영자는 시작 로그를 보고 안심하지만, 서버는 키가 없거나 틀린 요청도 그대로 처리한다. 로컬 stdio 방식에서는 문제가 없던 MCP 서버를 원격 HTTP로 띄우는 순간 네트워크 경계와 인증이 서버 구현의 몫이 되는데, 그 부분이 빠져 있었다.

## 플랫폼 엔지니어 관점
- 사내에서 HTTP 전송으로 띄운 MCP 서버를 찾아 3.0.1 이상으로 올리고, 키 없이 요청했을 때 401이 나오는지 직접 시험한다(‘인증 켜짐’ 로그를 믿지 않는다).
- Kubernetes에서는 MCP 서버 Service를 ClusterIP로 두고 NetworkPolicy로 호출 주체를 에이전트 파드로 한정한다. 인증은 서버 앞의 게이트웨이·사이드카에서 한 번 더 건다.
- MCP 서버 도입 체크리스트에 기본 바인딩 주소, 인증 강제 여부, 파일 접근 디렉터리 제한 옵션을 넣는다.
