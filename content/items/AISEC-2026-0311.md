## 요약
일본 AI 안전연구소(AISI)가 10월 30일 오픈 웨이트 모델 GLM-5.3의 익스플로잇 개발 능력을 평가한 검증 노트를 공개했다. V8 JavaScript 엔진의 알려진 취약점에서 만든 ExploitBench 과제 41개로 GLM-5.3, 이전 판 GLM-5.2, Claude Opus 4.8을 비교했다. GLM-5.3은 8개 과제에서 최고 단계(T1)에 올랐고 그중 7개는 실제로 임의 코드 실행까지 확인됐다. 한 세대 사이에 오픈 웨이트 모델의 고급 공격 능력이 크게 오른 셈이다. 동시에 첫 평가에서는 설정 문제로 GLM-5.3이 오히려 더 약하게 나왔다는 점을 숨기지 않고 적었다.

## 동작 원리
모델은 취약점 정보를 받아 익스플로잇 코드를 쓰고, 채점 도구를 불러 제출한다. 도구는 코드를 실제로 돌려 보고 메모리 손상 수준(T5)부터 실행 흐름 장악·임의 코드 실행(T1)까지 어디까지 갔는지 판정한다. 문제는 모델이 채점 도구를 부르지 않으면 아무리 좋은 코드를 써도 0점이 된다는 것이다. 첫 평가에서 GLM-5.3이 바로 그랬고, 추론 설정을 바로잡자 평균이 0.61에서 8.34로 뛰었다. 시험지를 다 풀고 답안지를 내지 않은 학생을 ‘못 푼다’고 채점한 것과 같다. 그래서 AISI는 평균 점수보다 과제별 도달 단계와 실행 로그를 함께 보라고 권한다.

## 플랫폼 엔지니어 관점
- 사내에서 오픈 웨이트 모델을 받아 서빙·에이전트에 붙이는 팀은 ‘오픈 모델은 공격 능력이 약하다’는 가정을 버린다. 모델 승인 절차에 외부 기관의 사이버 능력 평가 결과(버전·평가 조건 포함)를 기록하고, 고급 익스플로잇 능력이 보고된 모델은 코드 실행 도구·네트워크 접근을 기본 차단한 격리 환경에서만 쓰게 한다.
- 자체 레드팀·능력 평가 하네스를 운영한다면, 도구 호출 실패·추론 설정·타임아웃 같은 하네스 쪽 문제가 점수를 깎지 않았는지 실행 로그로 확인하는 단계를 CI 게이트에 넣는다. 평균 하나만 대시보드에 올리지 말고 과제별 최고 도달 단계를 함께 보인다.
- 취약점 관리 쪽에서는 V8·브라우저 엔진처럼 익스플로잇 개발 과제가 공개된 구성 요소를 쓰는 서비스(헤드리스 브라우저를 쓰는 브라우저 에이전트, 렌더링 서버)의 패치 우선순위를 올린다. AI가 익스플로잇을 쓰는 데 드는 시간이 줄수록 ‘알려졌지만 미패치’ 구간의 위험이 커진다.
