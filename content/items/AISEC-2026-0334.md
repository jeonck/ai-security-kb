## 요약
여러 데이터베이스를 MCP로 AI 어시스턴트에 연결해 주는 DBHub(Bytebase)의 읽기 전용 모드가 MySQL·MariaDB에서 우회됐다. 검증기와 DB가 같은 SQL 문자열을 다르게 읽는 ‘해석 차이’ 탓에, 공백 없는 -- 뒤에 숨긴 쓰기·DDL 문장이 검사를 통과하고 실제로 실행됐다. 권고는 6월 24일 0.22.6 수정과 함께 공개됐고, 10월 30일 CVE-2026-61789로 NVD·GitHub DB에 게시됐다. 권고 스스로 가장 현실적인 공격 경로를 어시스턴트가 읽는 콘텐츠 속 프롬프트 인젝션으로 꼽았다.

## 동작 원리
검문소(DBHub)는 ‘-- 뒤는 메모일 뿐’이라고 보고 지나가게 했지만, 목적지(MySQL·MariaDB)는 -- 바로 뒤에 공백이 없으면 그것을 빼기 기호로 읽는다. 게다가 검문소는 잘라서 검사한 조각이 아니라 원래 문자열 전체를 그대로 넘겼고, DB는 한 번에 여러 문장을 받도록 설정돼 있었다. 그 결과 ‘조회 한 건’으로 보인 요청이 DB에서는 ‘조회 + 테이블 삭제’가 됐다. 프롬프트 인젝션으로 모델이 이런 SQL을 만들게 하면, 사람은 ‘읽기 전용이니 안전’이라고 믿는 사이 데이터가 바뀐다.

## 플랫폼 엔지니어 관점
- DBHub를 쓰면 0.22.6 이상으로 올리고, MCP 서버가 쓰는 DB 계정 자체를 읽기 전용 역할(SELECT만 GRANT)이나 읽기 복제본으로 바꾼다. 도구 수준 ‘read-only 플래그’를 권한 통제로 세지 않는다.
- 다른 DB용 MCP 서버·에이전트 도구도 같은 패턴(문자열 검증 후 원문 실행, 다중 문장 허용)이 있는지 점검한다. 드라이버의 multipleStatements류 옵션은 기본으로 끈다.
- 에이전트가 쓰는 DB 연결에는 DDL·DML 감사 로그를 켜고, 읽기 전용으로 선언된 연결에서 쓰기가 나오면 경보를 울린다.
- 운영 DB를 에이전트에 붙일 때는 사람 승인 단계나 스냅샷·백업 복구 절차를 함께 설계한다.
