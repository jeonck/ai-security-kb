## 요약
Wiz는 2026-10-29 블로그에서 AI 에이전트가 침입의 손 작업 대부분을 맡고 사람은 목표와 제한만 정한 공격 3건을 직접 조사한 사례로 공개했다. 공격 A는 노출된 에이전트 빌더 Flowise를 인증 우회로 장악한 뒤 그것을 발판으로 다른 Flowise 수십 곳을 공격했고, 공격 C는 MCP 인터페이스를 가진 에이전트 백엔드에서 명령 인자를 셸로 넘겨 RCE를 얻은 뒤 클라우드 자격 증명과 Kubernetes 토큰을 빼내고 여러 파드로 퍼졌다. 공격 B는 Java 게이트웨이 RCE에서 시작해 4.5시간 동안 602단계를 실행했다. Wiz는 이 사례들과 ARTEX·Hermes 등 공개 사례를 묶어, 에이전트 사용을 가려내는 지문 기준 7가지를 제시했다.

## 동작 원리
에이전트형 공격자는 ‘손이 아주 빠르고 말이 많은 신입 침투 테스터’에 가깝다. 1~2분마다 새 스크립트를 쓰고, 스크립트 안에 계획과 이유를 자연어로 적고, 401·403 오류가 나면 다음 버전에서 고친 이유까지 남긴다. 한 목표만 파기보다 기법 목록을 위에서부터 차례로 시도하고, 측면 이동도 여러 경로에 동시에 뿌린다. 그래서 빠르지만 시끄럽다. 공격 C의 입구는 에이전트 플랫폼 자체였다. MCP 명령과 인자를 외부 입력에서 받아 subprocess로 넘기면, 그 인터페이스는 ‘도구 연결’이 아니라 원격 셸이 된다. 셸을 얻은 파드에 클라우드 자격 증명과 서비스 계정 토큰이 있었기 때문에 RCE 한 번이 비밀 대량 유출과 파드 간 확산으로 이어졌다.

## 플랫폼 엔지니어 관점
- Flowise 같은 에이전트 빌더와 MCP 엔드포인트를 인터넷에 직접 노출하지 않는다. 내부 요청 표시용 헤더처럼 ‘신뢰된 호출’ 표식을 인증 대신 쓰는 구성은 게이트웨이에서 외부 요청의 해당 헤더를 제거한다.
- MCP 서버의 stdio·명령 실행 설정은 외부 입력으로 바꿀 수 없게 고정하고, 명령·인자 허용 목록을 둔다. 에이전트 백엔드 파드에는 클라우드 자격 증명을 두지 말고 워크로드 ID와 최소 권한 역할만 준다. 서비스 계정 토큰 자동 마운트를 끄고 필요한 경우만 범위를 좁혀 투영한다.
- 런타임 탐지에 ‘에이전트 지문’을 넣는다. 짧은 간격으로 새 스크립트 파일 생성, 버전 접미사가 붙은 스크립트 반복, 무해한 표식 명령 뒤 실제 페이로드, 내부 호스트·포트 동시 스캔, 메모리 파일시스템(/dev/shm 등)의 실행 파일 같은 신호를 Falco·EDR 규칙으로 잡는다.
- 워크로드 egress를 허용 목록으로 묶어, 장악된 인스턴스가 다른 조직을 치는 발판이 되지 않게 한다.
- 정상 자동화(사내 코딩 에이전트·CI)와 구분할 수 있도록 승인된 에이전트의 신원·실행 위치·호출 패턴을 등록부로 관리한다. 등록되지 않은 위치에서 에이전트형 행동이 보이면 사고로 다룬다.
