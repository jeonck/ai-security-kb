## 요약
LLM이 만든 코드를 돌리는 샌드박스와 GPU 추론 엔드포인트를 제공하는 오픈소스 런타임 Beta9(Beam 클라우드의 엔진)에서 CVSS 9.9짜리 취약점 3건이 11월 1일 GitHub Advisory Database와 NVD에 등록됐다. 두 건은 샌드박스 파일 API와 볼륨 마운트의 경로 탐색이고, 한 건은 테넌트 이미지 빌드가 chroot로만 격리돼 특권 워커 파드의 네임스페이스를 그대로 공유한 문제다. 세 경우 모두 평범한 워크스페이스 토큰을 가진 테넌트가 워커 호스트 파일을 root로 다루고 다른 테넌트 데이터에 닿을 수 있었으며, 워커의 쿠버네티스 서비스 계정 토큰(배포 매니페스트상 cluster-admin)까지 노출됐다. 수정은 9월 15일 PR #1897로 이미 나왔지만 권고 등록은 약 7주 뒤였고, 권고의 버전 필드가 비어 있어 자동 의존성 경보도 뜨지 않는다.

## 동작 원리
샌드박스는 ‘방 안에서만 놀게 하는 것’인데, Beta9는 방 안 주소를 건물 주소로 바꿔 주는 안내원이 있었다. 안내원이 주소가 ‘방 안’으로 시작하는지 먼저 보고 나서 ‘..’(위층으로)를 정리했기 때문에, ‘방 안/../../../건물 기계실’ 같은 주소가 검사를 통과했다. 볼륨도 같은 식으로, 내 것인지 묻지 않고 이름만으로 경로를 조립하니 ‘..’ 섞인 이름으로 워커의 루트 디렉터리가 내 샌드박스에 쓰기 가능으로 붙었다. 이미지 빌드는 더 근본적인데, 각 RUN 명령이 파일시스템 루트만 바꾸고(chroot) 프로세스·네트워크 공간은 특권 워커와 공유했으므로 /proc/1/root로 워커 자신의 파일시스템을 들여다볼 수 있었다. 고친 방식은 경로를 os.OpenRoot로 ‘열린 루트 밖으로는 못 나가게’ 가두고, 빌드를 별도 네임스페이스와 OCI 격리로 돌리는 것이다.

## 플랫폼 엔지니어 관점
- Beta9를 자체 호스팅한다면 gateway 0.1.776·worker 0.1.756 이상인지 확인한다. 권고의 버전 필드가 비어 있어 Dependabot·SCA가 잡지 못하니 수동 점검이 필요하다.
- 워커 파드의 서비스 계정을 cluster-admin에서 떼어 내고, 필요한 네임스페이스 범위 권한으로 줄인다. 이번 사례에서 피해 반경을 결정한 것은 경로 버그가 아니라 이 바인딩이다. 의심되면 서비스 계정 토큰을 회수·재발급하고 감사 로그에서 워커 토큰의 비정상 API 호출을 찾는다.
- 사내 ‘에이전트 코드 실행’·‘노트북’·‘모델 빌드’ 플랫폼 전반에 같은 질문을 던진다: 테넌트 빌드가 chroot만으로 격리되는가, 워커가 privileged인가, hostPath 마운트에 소유권 검사가 있는가. 신뢰할 수 없는 코드를 돌리는 노드는 gVisor·Kata 같은 강한 격리와 전용 노드 풀로 분리한다.
- 서드파티 GPU·샌드박스 SaaS를 쓴다면 벤더에 테넌트 격리 모델(빌드 격리, 워커 권한, 패치 고지 정책)을 질의하고, 맡긴 시크릿은 ‘같은 워커의 다른 테넌트가 읽을 수 있다’는 가정 아래 범위를 최소화한다.
