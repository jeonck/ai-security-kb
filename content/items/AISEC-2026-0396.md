## 요약
CrewAI의 웹 스크래핑 도구는 에이전트가 넘긴 URL을 가져오기 전에 SSRF 검사를 한다. 그런데 검사기는 Python 표준 urlparse로, 실제 요청을 보내는 requests는 urllib3로 URL을 해석하고, 두 파서가 권한부의 백슬래시를 다르게 다룬다. 그래서 검사기는 공개 호스트라고 판정하고 클라이언트는 내부 주소로 연결한다. 보고자는 8월 초 CrewAI와 Langflow에 같은 기법을 보고했고, CrewAI는 8월 17일 연결 시점에 검증된 IP로 고정하는 방식으로 고쳤다. CVE는 그로부터 석 달 뒤인 11월 2일 CERT/CC가 붙였다.

## 동작 원리
문지기와 운전기사가 같은 주소 쪽지를 서로 다른 방식으로 읽는 상황이다. 문지기는 쪽지에서 ‘공개된 회사 주소’를 읽고 통과시키지만, 운전기사는 같은 쪽지에서 ‘사내 금고 주소’를 읽고 그리로 간다. 프롬프트 인젝션으로 에이전트가 이런 URL을 스크래핑 도구에 넘기게 만들면, 에이전트가 도는 서버의 위치에서 클라우드 메타데이터나 내부 관리 화면으로 요청이 나가고 응답이 모델 컨텍스트로 돌아온다. 경로에 /../를 섞어 내부 서비스가 깔끔한 경로를 받게 만드는 것도 보고자가 쓴 방법이다. 근본 해결은 ‘문자열을 검사하고 다시 해석’하지 않고, 이름을 한 번만 풀어 그 IP로만 연결하고 연결된 상대를 다시 확인하는 것이다.

## 플랫폼 엔지니어 관점
- CrewAI(또는 crewai-tools)를 1.15.17 이상으로 올린다. GHSA가 아직 검토 전이라 패키지·버전이 비어 Dependabot이 경보를 띄우지 않으므로, 의존성 목록을 직접 확인한다.
- 앱 계층 SSRF 검사는 보조 수단으로만 본다. 에이전트 워커 파드에 NetworkPolicy·egress 프록시로 169.254.169.254와 클러스터 내부 CIDR을 막고, 클라우드는 IMDSv2(홉 제한 1)를 강제한다.
- 멀티테넌트 워커에서는 CREWAI_TOOLS_FORCE_SAFE_PATHS를 켜서 개별 작업이 안전 설정을 풀지 못하게 한다.
- 사내에서 만든 URL 검사 코드가 검사용 파서와 요청용 파서를 따로 쓰는지 점검한다. 백슬래시·%5c 포함 URL을 거부하는 테스트를 CI에 넣는다.
