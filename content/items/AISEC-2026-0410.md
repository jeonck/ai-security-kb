## 요약
2026-11-02 IETF에 ‘Bounded Capabilities for Agent Tool Interfaces: Problem Statement’ -01이 올라왔다. MCP 같은 에이전트 도구 프로토콜이 JSON Schema로 입력·출력 형식을 선언하지만, 그 선언은 계약이 아니어서 인가·발견·감사·조합을 결정적으로 처리할 수 없다는 문제 제기다. 경계 여부 미표시, 자가 인증, 선언 미고정, 비정형 오류, 모델 매개의 비가시성이라는 다섯 빈틈을 정리하고 해법 대신 열린 질문 7개를 던진다. 단일 저자의 개인 초안으로 IETF 합의는 없다.

## 동작 원리
식당 메뉴판을 생각하면 쉽다. 메뉴판(도구 스키마)에 ‘오늘의 요리’라고만 적혀 있으면 손님(정책 엔진)은 무엇이 나올지 알 수 없다. 메뉴판은 주방이 스스로 쓰고(자가 인증), 주문을 받은 뒤 바뀔 수도 있으며(선언 미고정), 재료가 떨어졌다는 말도 자유 문장으로 돌아온다(비정형 오류). 게다가 요리를 사람이 했는지 기계가 했는지(모델 매개)도 알 수 없다. 그래서 ‘이 호출을 허용할까’, ‘이 로그가 정상인가’를 판단하려면 결국 또 다른 LLM에 해석을 맡기게 되고, 판단이 재현되지 않는다. 초안은 범위가 정해진 도구와 열린 도구를 구분해 표시하는 것부터 필요하다고 본다.

## 플랫폼 엔지니어 관점
- MCP 게이트웨이·프록시에서 도구 목록과 스키마의 해시를 승인 시점에 고정하고, 호출 시점 스키마가 다르면 차단하거나 재승인하게 한다(TOCTOU 대응).
- 사내 MCP 서버는 입력 스키마를 열린 object로 두지 말고 필드·형식·enum을 좁혀, 정책 엔진(OPA 등)이 LLM 없이 판정할 수 있는 형태로 만든다. 출력 스키마와 구조화된 오류 코드도 정의한다.
- 감사 로그에 산문 요청만 남기지 말고 도구 이름·스키마 해시·구조화된 인자·결정 결과를 함께 남겨, 사후에 같은 정책으로 재검증할 수 있게 한다.
- 열린 형식의 도구(셸, 범용 HTTP 등)는 별도 등급으로 분류해 격리·승인 단계를 더 강하게 건다.
