## 요약
MCP 명세는 데이터 삭제·송금 같은 파괴적 도구 호출을 사람이 거부할 수 있어야 한다고 하지만, 그 책임은 서버(도구 주석·엘리시테이션)와 호스트(프롬프트 표시 여부)에 나뉘어 있다. 연구진은 공식 레지스트리의 1,000개 저장소와 오픈소스 호스트·SDK 41개를 소스 코드 수준에서 조사해, 양쪽 모두 기본값으로는 사람을 끼워 넣지 않는 경우가 대부분임을 보였다. 서버 쪽 파괴적 도구의 약 90%는 확인 절차가 없고, 호스트 41개 중 32개는 기본 승인 단계가 없었다. 실제로 SDK 4종에서 주입된 삭제 지시가 절반 가까이 실행됐다. 연구진은 엘리시테이션 지원을 늘리는 것만으로는 부족하고, 호스트가 ‘읽기 전용으로 표시되지 않은 모든 도구’에 대해 묻는 정책이 효과적이라고 결론 내렸다.

## 동작 원리
은행 창구에 비유하면, 창구 직원(서버)은 ‘본인 확인은 지점장(호스트)이 하겠지’라고 생각하고, 지점장은 ‘위험한 거래면 창구에서 물어보겠지’라고 생각하는 상황이다. 서버가 붙이는 destructiveHint 같은 주석은 표시일 뿐 강제가 아니며, confirm=true 같은 확인 플래그는 모델이 직접 채울 수 있어 프롬프트 인젝션이 그 값을 같이 넣으면 무력화된다. 엘리시테이션도 호스트가 질문을 사용자에게 전달하지 못하면 많은 서버가 그냥 진행하도록 짜여 있다. 결국 사람이 개입하는 유일한 지점은 호스트가 실행 전에 띄우는 승인 창인데, 대부분의 SDK는 이를 기본으로 꺼 두고 옵션으로만 제공한다.

## 플랫폼 엔지니어 관점
- 사내 에이전트를 OpenAI Agents SDK·LangChain MCP 어댑터·crewAI·Google ADK 등으로 만든다면, 기본값에 기대지 말고 SDK의 승인 옵션이나 pre-call 훅을 명시적으로 켠다. ‘readOnlyHint/비파괴로 표시되지 않은 도구는 모두 승인’을 기본 정책으로 두고 예외 목록을 관리한다.
- 서버의 확인 플래그(confirm, force 등)는 모델이 채울 수 있으므로 승인 수단으로 간주하지 않는다. 사내 MCP 서버는 엘리시테이션을 전달받지 못하면 실패(fail-closed)하거나 미리보기만 반환하도록 리뷰 기준에 넣는다.
- 헤드리스·CI 실행(예: 배치형 에이전트)에서는 승인 창이 뜰 수 없으므로 파괴적 도구 자체를 노출하지 않거나, 쓰기 자격 증명을 분리한 별도 워크로드에서만 허용한다.
- MCP 게이트웨이가 있다면 도구 주석과 무관하게 삭제·결제·권한 변경 계열 호출을 게이트웨이에서 정책으로 차단·보류하는 계층을 둔다.
