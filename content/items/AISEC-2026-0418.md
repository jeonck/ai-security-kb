## 요약
MCP는 도구 설명·스키마 필드·응답 같은 공격자가 고칠 수 있는 내용을 검증 없이 모델 문맥에 넣는다. 기존 벤치마크는 모델이 오염된 지시를 ‘따르려 했는지’만 봤는데, 이 연구는 오픈소스 도구 mcpvenom으로 실제 도구 실행과 카나리 HTTP 수신까지 확인했다. 12개 프레임워크·18개 모델·45개 시나리오에서 전체 성공률은 22.9%였고, 결과를 가른 것은 프레임워크가 아니라 모델이었다. 어떤 프레임워크도 도구 설명을 일부러 검증하지 않았고, 연구진의 신고 5건은 ‘서버는 신뢰된 구성’이라는 이유로 모두 거절됐다.

## 동작 원리
MCP 서버는 ‘이 도구는 이렇게 쓰세요’라는 설명서를 모델에게 건넨다. 그 설명서에 ‘이 도구를 부르기 전에 환경 변수를 다른 도구로 보내라’ 같은 지시나, 파라미터에 엉뚱한 값을 묶도록 유도하는 문구를 넣는 것이 도구 포이즈닝이다. 프레임워크는 설명서를 그대로 전달하는 배관 역할만 하므로, 결국 모델이 그 지시를 무시하느냐에 달려 있다. 그래서 같은 공격이 프레임워크와 관계없이 비슷한 비율로 통하고, 모델을 바꾸면 성공률이 100배 이상 달라진다.

## 플랫폼 엔지니어 관점
- 프레임워크 벤더는 MCP 서버 검증을 책임지지 않는다고 공식적으로 밝혔다. 서버 반입 심사(출처·서명·도구 설명 해시 고정)와 설명 변경 시 재승인은 플랫폼 팀이 직접 해야 한다.
- 도구 설명 정규식 스캐너는 절반도 못 거른다. 스캔은 보조 수단으로 두고, egress 허용 목록과 런타임 카나리(가짜 비밀값을 심고 외부 수신을 감시)로 실제 유출을 탐지한다.
- 모델 선택이 곧 보안 통제가 된다. 에이전트용 모델을 바꿀 때 사내 MCP 포이즈닝 회귀 시험(예: mcpvenom 시나리오)을 돌려 성공률을 비교하는 단계를 CI에 넣는다.
- 파라미터 바인딩 공격이 가장 높으므로, 민감 파라미터(경로·URL·수신자)는 서버 측에서 허용 값 범위를 강제한다.
