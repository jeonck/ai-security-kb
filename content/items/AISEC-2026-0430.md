## 요약
MAESTRO는 CSA 블로그에 Ken Huang(DistributedApps.ai)이 2025-02-06 발표한 에이전트 AI 위협 모델링 프레임워크다. 저자는 먼저 STRIDE·PASTA·LINDDUN·OCTAVE·Trike·VAST를 하나씩 비교해, 이들이 적대적 ML·데이터 오염, 자율적이고 비결정적인 행동, 에이전트 간 공모·경쟁 같은 위협을 담지 못한다고 진단한다. 대안으로 에이전트 시스템을 기반 모델(L1)부터 데이터 운영, 에이전트 프레임워크, 배포·인프라, 평가·관측, 보안·컴플라이언스, 에이전트 생태계(L7)까지 7계층으로 나누고 계층마다 위협 목록을 붙였다. 한 계층의 약점이 다른 계층으로 번지는 계층 간 위협을 따로 다루고, 시스템 분해부터 지속 모니터링까지 6단계 절차와 계층별·계층 간·AI 특화 완화 전략을 제시한다.

## 동작 원리
STRIDE가 데이터 흐름도 위의 각 상자에 같은 여섯 가지 질문을 던지는 방식이라면, MAESTRO는 먼저 상자들을 에이전트 시스템 고유의 층으로 정렬한 뒤 층마다 다른 질문 목록을 꺼내는 방식이다. 모델 층에는 백도어·모델 탈취를, 데이터 층에는 RAG 오염을, 인프라 층에는 컨테이너 이미지·IaC 조작을, 생태계 층에는 에이전트 사칭·레지스트리 오염을 묻는다. 보안·컴플라이언스 층(L6)은 다른 층 위에 얹힌 것이 아니라 모든 층을 세로로 관통하며, 보안 도구로 쓰이는 AI 에이전트 자체의 오염·회피까지 위협으로 본다. 핵심은 계층 간 사슬이다. 인프라 침해(L4) → 데이터 오염(L2) → 다음 모델 갱신 오염(L1)처럼 층별로는 사소한 약점이 이어져 큰 사고가 된다. 그래서 층별 점검으로 끝내지 않고 사슬을 따라가며 위험 매트릭스로 우선순위를 정하고, 시스템이 바뀔 때마다 모델을 다시 돌린다.

## 플랫폼 엔지니어 관점
- MAESTRO 7계층을 플랫폼 구성요소와 담당 팀에 대응시킨 표를 만든다. 예: L1 모델 레지스트리·서빙(ML 플랫폼팀), L2 벡터 DB·RAG 파이프라인(데이터팀), L3 에이전트 프레임워크·MCP 서버 의존성(앱팀), L4 Kubernetes 클러스터·컨테이너 이미지·IaC(플랫폼팀), L5 트레이싱·평가 파이프라인(SRE), L6 정책 엔진·감사 로그(보안팀), L7 내부 에이전트 카탈로그·에이전트 간 연동(플랫폼 거버넌스). 담당 팀이 비는 층이 곧 리스크 등록부의 첫 항목이다.
- 에이전트 온보딩(카탈로그 등록) 때 MAESTRO 6단계를 따른 위협 모델 문서를 승인 게이트의 필수 산출물로 두고, 위험 매트릭스 점수가 기준을 넘으면 egress·도구 권한을 줄인 상태로만 승인한다. 모델·프레임워크·도구가 바뀌면 재검토를 자동으로 요구한다(6단계의 지속 갱신).
- 계층 간 사슬을 레드팀 시나리오로 넘긴다. 노드·이미지 침해 → 에이전트 파드에서 벡터 DB 쓰기 → 다음 파인튜닝 데이터 오염. 각 고리를 끊는 통제(이미지 서명 admission, 벡터 DB 쓰기 권한 분리, 학습 데이터 계보 검증)가 실제로 작동하는지 확인한다.
- L5 관측 계층 자체를 공격 표면으로 다룬다. 프롬프트·도구 출력이 담긴 트레이스 저장소의 접근 권한과 보존 기간을 제한하고, 평가 데이터셋·지표 파이프라인을 누가 바꿀 수 있는지 감사한다.
- L7 위협(에이전트 사칭·레지스트리 오염·부인)에 대비해 에이전트마다 워크로드 ID를 발급하고, 에이전트 간 호출은 상호 인증으로, 모든 도구 호출은 호출 주체 ID와 함께 기록한다.
