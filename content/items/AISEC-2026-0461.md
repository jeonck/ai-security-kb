## 요약
MCP 서버 대부분은 공식 Python·TypeScript SDK 위에 만들어진다. 이 논문은 SDK가 명세에 적힌 제약(형식, 범위, 필수 필드, 기능 협상 규칙)을 실제로 강제하는지 따져 보는 MCPGuard를 만들어, 두 SDK에서 모두 32건의 미검사 제약을 찾았다. 공식 적합성 스위트와 서드파티 검사기는 모든 검사를 통과시켰고 이 틈을 하나도 잡지 못했다. 공개 MCP 서버 32곳을 찔러 보니 SDK의 틈이 그대로 서버까지 이어졌다. 결과는 유지 관리자에게 비공개로 보고돼 확인을 받았고, 공개는 수정 뒤로 미뤘다.

## 동작 원리
건물 설계 도면(명세)에는 ‘이 문은 직원 카드로만 열린다’고 적혀 있는데, 시공사(SDK)가 실제로 카드 리더를 달았는지는 아무도 확인하지 않은 상황과 같다. 기존 적합성 검사는 완성된 건물에 정상 카드를 대 보고 문이 열리는지만 보니, 카드 없이도 열리는지는 모른다. MCPGuard는 도면의 숫자·형식 조건을 SDK의 데이터 모델과 한 줄씩 맞대 보고(구조 트랙), 문장으로 된 규칙은 관련 함수 코드를 잘라 LLM에게 ‘이 규칙을 검사하는 코드가 있나’를 묻는다(행동 트랙). 후보는 실제 테스트를 만들어 재현될 때만 인정한다. 잘못된 URI 같은 값은 그 자체로는 사소해 보이지만, 그것을 렌더링하거나 저장하거나 역참조하는 하위 코드로 흘러가면 공격 경로가 된다.

## 플랫폼 엔지니어 관점
- 사내 MCP 서버를 승인할 때 공식 적합성 스위트 통과를 안전 근거로 삼지 않는다. 서버 쪽에서 URL·URI·수치 필드를 SDK와 별도로 다시 검증하도록 요구한다.
- MCP SDK 버전을 SBOM에 남기고, 이 연구의 공개(수정 버전·GHSA)가 나오면 영향받는 서버를 바로 찾을 수 있게 한다.
- MCP 게이트웨이에 명세 위반 메시지(형식이 틀린 URI, 범위 밖 수치, 광고하지 않은 기능 요청)를 거부·기록하는 스키마 검증 단계를 둔다.
- 사내 MCP 서버용 퍼징·부정 입력 테스트를 CI에 넣어, 정상 입력 위주의 적합성 테스트를 보완한다.
