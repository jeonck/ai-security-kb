## 요약
MCP 서버·도구에 서명을 붙이고 런타임 egress 정책을 거는 것이 공급망 방어의 표준 처방이 되고 있다. 이 논문은 둘 다 통과하는 악성 도구를 만들었다. 정상적으로 OCR을 해 주면서 이전 호출에서 본 데이터를 다음 요청에 몰래 붙여 ‘허가된’ OCR 서버로 보내는 식이다. Meta의 MCPGuard-Dynamic을 포함한 기존 방어는 153회 실행 중 5.9~74.5%에서 유출을 허용했고, egress 허용 목록은 허용 호스트로 보내는 변형 20개를 전혀 막지 못했다. 저자들은 호출마다 데이터 없는 원형에서 복제본을 떠 목적지별로 받아도 되는 데이터만 주는 ‘germline execution’을 제안해 유출 0건을 보고했다.

## 동작 원리
택배 기사가 신분증도 확인됐고 배달처도 허가된 주소뿐이라도, 상자 속에 지난번 고객의 서류를 끼워 넣으면 막을 수 없다. 서명은 ‘누가 만들었나’, egress 정책은 ‘어디로 가나’만 본다. 이 공격은 ‘무엇을 싣고 가나’를 노린다. 해결책은 기사가 애초에 지난번 고객 서류를 갖고 있지 못하게 하는 것이다. 호출마다 깨끗한 복제본을 쓰고, 그 복제본에는 이번 목적지가 받아도 되는 데이터만 준다.

## 플랫폼 엔지니어 관점
- MCP 서버 승인 기준을 ‘서명·출처 확인’에서 끝내지 않는다. 서명은 침해된 게시자나 악의적 게시자의 정상 서명 릴리스를 걸러 내지 못한다.
- egress 허용 목록은 필요조건이지 충분조건이 아니다. 허용 목적지(SaaS OCR·번역 API 등)로 나가는 요청 본문 크기·필드를 기준선과 비교하는 탐지를 붙인다.
- 상태를 유지하는 장기 실행 MCP 서버 컨테이너보다 호출 단위로 초기화되는 실행(요청별 컨테이너·microVM·스냅샷 복원)을 우선 검토하고, 도구가 읽을 수 있는 파일 범위를 호출 단위로 좁힌다.
- 한 도구가 여러 목적지로 데이터를 보낸다면 목적지별 데이터 분류(라벨)를 정해 두고, 에이전트 게이트웨이에서 라벨과 목적지가 맞는지 확인한다.
