## 요약
UC Berkeley(Raluca Popa·David Wagner·Julien Piet 등)와 KACST 연구진이 웹 에이전트용 ‘컴파일 후 실행’ 설계 Baya를 발표했다. 매 단계 화면을 보고 다음 행동을 고르는 ReAct 방식은 신뢰할 수 없는 웹 콘텐츠가 제어 흐름에 섞여 인젝션에 약하다. Baya는 요청을 먼저 신뢰 API를 부르는 Python 프로그램으로 컴파일하고, 라이브 웹 콘텐츠는 그 프로그램만 처리하게 한다. WebArena Verified에서 유용성이 오히려 높았고(77.8%), WASP 인젝션 공격은 모두 실패했다. 대신 과제당 지연·비용이 ReAct의 약 4~5배다.

## 동작 원리
ReAct 에이전트는 길을 걸으며 표지판을 읽고 그때그때 방향을 바꾸는 여행자다. 누군가 가짜 표지판을 세우면 따라간다. Baya는 출발 전에 지도(사이트의 신뢰 API 목록)만 보고 경로를 코드로 짜 둔다. 걷는 중에 읽는 표지판(댓글·리뷰·게시물)은 ‘어느 가게에 들를지’ 같은 미리 정해 둔 선택지 안에서만 값을 고를 수 있고, 새 행선지를 만들 수 없다. 계획을 짠 모델은 표지판을 아예 보지 않는다.

## 플랫폼 엔지니어 관점
- 사내 업무 에이전트(GitLab·티켓·쇼핑몰 관리 등)는 브라우저 자유 조작보다 타입이 있는 API 카탈로그(전·후조건 포함)를 먼저 제공하는 쪽이 보안과 성공률을 함께 올린다는 근거로 쓸 수 있다.
- 계획 단계(모델·도구 접근)와 실행 단계(라이브 데이터 처리)를 별도 프로세스·권한으로 나누고, 실행 중 오류가 계획 모델로 되돌아갈 때 원본 웹 데이터가 섞이지 않게 진단 메시지를 정형화한다.
- 생성된 프로그램을 실행 전에 저장·검토할 수 있으므로, 고위험 작업은 프로그램 단위 승인과 감사 로그를 붙인다.
- 지연·비용 증가(과제당 약 327초)를 감안해 캐시·재사용 가능한 반복 업무부터 적용하고, 탐색형 작업은 기존 방식에 더 강한 egress·권한 통제를 건다.
