## 요약
오픈소스 멀티 에이전트 프레임워크 AgentScope의 결함 3건이 2026-11-05 VulDB를 통해 CVE로 게시됐다. 독립 연구자 Yongbo Yu가 10월 14일 공개 권고와 이슈로 알린 내용으로, (1) Agent Service가 X-User-ID 헤더를 검증 없이 신원으로 쓰는 인증 부재(CVE-2026-123024), (2) MCP stdio 설정의 command 문자열이 그대로 프로세스로 실행되는 명령 주입(CVE-2026-123022), (3) Bash 도구 권한 엔진이 tee를 읽기 전용으로 분류해 확인 없이 파일을 쓰는 결함(CVE-2026-123023)이다. 세 번째만 2.0.9에서 고쳐졌고, 앞의 두 건은 수정 PR이 병합되지 않은 채 2.0.11까지 영향을 받는다. 연구자는 첫 두 건을 묶으면 네트워크에서 인증 없이 서버 명령을 실행할 수 있다고 평가했다.

## 동작 원리
- 인증 부재: 서버는 ‘나는 alice다’라고 적힌 이름표(X-User-ID)를 확인 없이 믿는다. 모든 테넌트 데이터가 그 이름표 값으로 나뉘어 저장되므로, 이름표만 바꾸면 남의 자격 증명(LLM API 키)과 에이전트를 마음대로 다룬다.
- MCP stdio: stdio 방식 MCP 서버는 ‘이 명령을 실행해 표준 입출력으로 대화하라’는 설정이다. 즉 설정 자체가 실행 명령이다. AgentScope는 설정을 저장하는 순간 연결을 시도하므로, 저장 API를 부를 수 있는 사람은 곧 서버에서 아무 명령이나 실행할 수 있다. 핸드셰이크가 실패해 오류가 나도 프로세스는 이미 돈 뒤다.
- tee 오분류: 셸 도구는 ‘읽기만 하는 명령’은 묻지 않고 실행하는 빠른 길을 둔다. tee는 입력을 화면과 파일에 동시에 쓰는 명령인데 이 목록에 들어 있어, 모델이 echo … | tee ~/.ssh/authorized_keys 를 만들면 확인 없이 키가 심어졌다. > 리다이렉션은 막고 파이프+tee는 놓친 셈이다.

## 플랫폼 엔지니어 관점
- AgentScope Agent Service를 쓰는 팀은 즉시 127.0.0.1 바인딩 또는 인증 리버스 프록시 뒤로 옮기고, 프록시에서 들어오는 X-User-ID 헤더를 제거한 뒤 검증된 토큰에서 신원을 주입한다. Kubernetes라면 Service를 ClusterIP로만 두고 Ingress에 OIDC 인증을 건다.
- MCP stdio 설정을 API로 받는 모든 에이전트 플랫폼에서 ‘설정 저장 = 원격 명령 실행’으로 위협 모델을 다시 쓴다. command는 서버 측 허용 목록(고정 경로의 승인된 실행 파일)으로만 받고, 사용자 정의 stdio는 원격 노출 배포에서 기본 비활성화한다. 프록시·WAF에서 POST /workspace/mcp를 차단하는 것도 임시 완화책이다.
- stdio MCP 프로세스는 파일시스템·네트워크·환경 변수가 최소화된 샌드박스(별도 컨테이너, gVisor 등)에서 띄우고, 서버 프로세스의 LLM API 키가 자식 프로세스 환경으로 상속되지 않게 한다.
- 에이전트의 셸 명령 허용 목록은 ‘명령 이름’이 아니라 ‘효과(파일 쓰기·네트워크·프로세스 생성)’ 기준으로 검토하고, tee·sed -i·git config 등 쓰기 효과가 있는 명령을 정기 감사한다. 허용 목록보다 쓰기 가능한 경로 자체를 줄이는 읽기 전용 루트 파일시스템이 더 견고하다.
- 2.0.9 이상으로 올리되, 남은 두 CVE는 미수정이므로 버전 업그레이드만으로 닫히지 않는다는 점을 위험 등록부에 적는다.
