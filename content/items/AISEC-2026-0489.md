## 요약
자연어로 데이터베이스를 다루는 LLM 에이전트 프레임워크 DB-GPT의 결함 3건이 2026-11-05 VulDB를 통해 CVE로 게시됐다. 독립 연구자 Yongbo Yu가 10월 14일 공개 권고로 알린 것으로, 가장 심각한 CVE-2026-123018은 CodeEngineer 에이전트가 모델이 낸 코드 블록을 실행할 때 컨테이너 안에서는 오히려 Docker 샌드박스를 건너뛰는 논리 오류다. 기본 배포는 인증이 사실상 없어, 네트워크로 접근한 누구나 모델에게 코드 블록을 내게 하는 평범한 요청만으로 서버에서 명령을 실행할 수 있다. CVE-2026-123019는 Hugging Face 모델 등록 시 trust_remote_code가 기본 True라 악성 모델 저장소 코드가 서버에서 실행되는 문제다. 두 건은 벤더 응답과 수정이 없고, 스킬 템플릿 결함(CVE-2026-123020)만 0.8.2에서 고쳐졌다.

## 동작 원리
CodeAction의 실행기는 ‘Docker를 쓰지 않거나, 이미 컨테이너 안이면 그냥 로컬에서 실행한다’는 분기를 갖고 있다. 의도는 ‘컨테이너 안에서 컨테이너를 또 띄우지 말자’였겠지만, 공식 배포가 Docker 컨테이너이므로 이 조건은 항상 참이 되고 모델 출력 코드는 DB-GPT 서버 프로세스 권한으로 그대로 실행된다. 서버 컨테이너에는 LLM API 키와 내부 DB 접속 정보가 있으니, 샌드박스가 아니라 금고 안에서 코드를 돌리는 셈이다. 여기에 코드 블록을 자동으로 뽑아 실행하고 확인 단계(review)가 늘 통과하는 구조가 겹쳐, 프롬프트 한 줄이 곧 원격 명령이 된다. HF 경로는 ‘모델 로드 = 저장소의 파이썬 import’라는 trust_remote_code의 성질을 기본값으로 열어 둔 문제다.

## 플랫폼 엔지니어 관점
- DB-GPT를 운영 중이면 5670 포트를 신뢰된 네트워크로 제한하고 인증 리버스 프록시 뒤에 둔다. 수정 릴리스 전까지 CodeEngineer/CodeAction 앱을 끄고, Docker SDK 설치를 완화책으로 믿지 않는다.
- 에이전트 코드 실행은 ‘에이전트 서버와 같은 컨테이너’가 아니라 자격 증명이 없는 별도 샌드박스(일회용 Pod, gVisor·Kata 등)로 보낸다. ‘이미 컨테이너 안’이라는 판단은 격리를 의미하지 않는다는 점을 설계 리뷰 체크리스트에 넣는다.
- 런타임 탐지: 에이전트 서버 컨테이너에서의 예상 밖 자식 프로세스 생성과 임시 코드 스크립트 실행을 Falco·Tetragon 규칙과 로그 알림으로 잡는다.
- 모델 로더의 trust_remote_code는 조직 정책으로 기본 False로 고정하고, 허용된 모델 저장소 목록(내부 미러·서명 확인)에서만 로드한다. 모델 등록 API는 관리자 인증 뒤로 둔다.
- 오픈소스 에이전트 프레임워크 도입 시 ‘기본 인증이 mock인지’, ‘0.0.0.0 바인딩이 기본인지’를 도입 심사 항목으로 둔다. 같은 날 같은 연구자의 AgentScope 권고(AISEC-2026-0488)도 CVE로 게시됐다.
