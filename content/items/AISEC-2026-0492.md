## 요약
Go용 MCP SDK인 mcp-go와 이를 포함한 터미널 AI 에이전트 ChatCLI의 MCP OAuth 클라이언트에서, 접속한 MCP 서버가 스스로 밝힌 ‘보호 자원(resource)’ 값을 검증 없이 믿는 결함이 드러났다. 클라이언트는 그 값을 그대로 RFC 8707 자원 지시자로 써서 인가 서버에 토큰을 요청했기 때문에, 악성이거나 침해된 MCP 서버가 같은 인가 서버에 붙은 다른 서비스를 자원으로 적어 내면 사용자는 그 다른 서비스용 토큰에 동의하게 되고, 토큰은 다시 악성 서버로 전달됐다. 같은 연구자가 10월 초 두 프로젝트에 신고해 mcp-go 1.2.1과 ChatCLI 1.215.2에서 고쳐졌고, 2026-11-05 GitHub Advisory Database에 CVE로 게시됐다.

## 동작 원리
택배 기사가 ‘이 물건은 옆 건물 금고실 앞으로 받아 주세요’라고 적힌 쪽지를 내밀었을 때, 경비가 그 쪽지가 정말 이 기사의 건물을 가리키는지 확인하지 않고 옆 건물 출입증을 발급해 주는 꼴이다. MCP 인가 흐름에서 클라이언트는 서버의 well-known 메타데이터(RFC 9728)로 ‘이 서버의 자원 이름’을 알아낸 뒤, 그 이름을 RFC 8707 resource 파라미터에 넣어 ‘이 자원에만 쓸 수 있는 토큰’을 받는다. 원래 RFC 9728 §3.3은 메타데이터가 말하는 자원이 지금 접속한 주소와 같은지 대조하라고 요구한다. 이 대조가 빠지면, audience를 좁히려고 넣은 자원 지시자를 상대 서버가 마음대로 정할 수 있게 되고, 결과적으로 사용자가 동의한 토큰은 악성 서버가 고른 ‘다른 서비스’ 앞으로 발급된다.

## 플랫폼 엔지니어 관점
- 사내 에이전트·MCP 클라이언트가 Go로 짜였다면 go.mod에서 github.com/mark3labs/mcp-go 버전을 찾아 1.2.1 이상으로 올리고, ChatCLI 사용자는 1.215.2로 올린 뒤 신뢰하지 않은 서버 로그인 이력이 있으면 로그아웃·클라이언트 철회를 한다.
- 인가 서버(사내 IdP) 쪽에서 MCP 클라이언트의 동적 클라이언트 등록을 허용한다면, 등록 시 허용할 resource 목록을 서버별로 미리 등록해 두고 그 밖의 자원 지시자 요청은 거부한다. 클라이언트 구현을 믿지 않고 IdP에서 한 번 더 막는다.
- 하나의 인가 서버에 여러 내부 MCP 서버·API를 붙여 두는 구성은 이 공격의 전제 조건이다. 민감 자원은 별도 인가 서버 또는 별도 클라이언트 등록으로 분리하고, 토큰 감사 로그에서 ‘MCP 클라이언트가 요청한 resource ≠ 실제 연결 서버’ 패턴을 탐지 규칙으로 만든다.
- 자체 MCP 클라이언트를 만든다면 resource 값은 설정한 서버 URL에서 정규화해 만들고, 서버가 준 값은 대조용으로만 쓴다. resource_metadata URL은 같은 출처일 때만 따라간다.
