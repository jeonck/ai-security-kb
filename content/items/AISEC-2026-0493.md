## 요약
LLM 앱과 에이전트 워크플로를 만드는 플랫폼 Dify는 워크플로의 코드 노드를 별도 샌드박스 컨테이너에서 실행한다. 이 샌드박스는 API 키로 요청을 인증하지만, 키의 기본값 dify-sandbox가 설정 예시 파일을 포함한 네 곳에 박혀 있어 빠른 시작 절차를 그대로 따른 배포는 모두 같은 공개 키를 쓴다. 미들웨어용 Compose 파일로 띄우면 샌드박스가 호스트 8194 포트로 열리기 때문에, 그 포트에 닿는 누구나 키를 넣어 임의 Python·JS 코드를 실행할 수 있었고 샌드박스는 기본으로 외부 네트워크에도 나갈 수 있었다. 신고자는 7월 비공개 신고 후 응답이 없자 10월 공개했고, 11월 5일 CVE로 게시됐지만 수정 릴리스는 아직 없다.

## 동작 원리
금고에 비밀번호 자물쇠를 달아 두고 설명서 첫 장에 ‘초기 비밀번호: 0000’을 인쇄해 둔 셈이다. 인증 검사는 분명히 있어서 틀린 키는 401로 막히지만, 맞는 키가 모두에게 같은 공개 문자열이라 인증의 의미가 없다. 샌드박스는 원래 ‘믿을 수 없는 코드를 돌려도 되는 곳’이라서 코드 실행 자체가 기능이다. 그래서 문(포트)이 바깥으로 열리고 열쇠(기본 키)가 공개되면, 샌드박스는 격리 장치가 아니라 누구나 쓰는 원격 코드 실행 서비스가 되고, 네트워크 기본 허용 때문에 외부 공격의 발판으로도 쓰일 수 있다.

## 플랫폼 엔지니어 관점
- Dify를 자체 호스팅한다면 SANDBOX_API_KEY와 CODE_EXECUTION_API_KEY가 dify-sandbox가 아닌지 즉시 확인하고 무작위 값으로 바꾼다. 미들웨어 Compose로 띄웠다면 middleware.env에도 같은 변경을 반영한다.
- 8194 포트를 호스트·LoadBalancer·NodePort로 열지 않는다. Kubernetes라면 샌드박스 파드에 NetworkPolicy로 Dify API 파드에서 오는 인바운드만 허용하고, 샌드박스 egress는 필요한 목적지만 열거나 기본 차단한다.
- 설정 예시 파일(.env.example)을 그대로 복사하는 배포 관행 자체를 점검한다. Helm values·Compose에서 기본 시크릿을 쓰면 기동을 실패시키는 정책(예: CI에서 알려진 기본값 문자열 검사, Kyverno·OPA로 시크릿 값 검증)을 둔다.
- 코드 실행 샌드박스는 ‘격리 계층’이자 ‘공격 표면’이다. 샌드박스 API 호출 로그와 비정상적인 외부 접속을 탐지 대상으로 넣는다.
