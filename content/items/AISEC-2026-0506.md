## 요약
Google Cloud가 2026-11-04 Security Summit과 보안 블로그에서 에이전트가 실행되는 환경 전반(Gemini, GKE, Cloud Run, Agent Compute Engine)에 공통 보안·거버넌스 통제를 넓힌다고 발표했다. 핵심은 신원이다. 자격 증명을 IAM이 관리하는 금고에 모으는 Auth Manager가 GA가 됐고, 에이전트가 AWS·Azure·온프레미스·MCP 서버에 정적 키 없이 OIDC 토큰으로 인증하는 Agent Identity JWT가 프리뷰로 나왔다. 네트워크 쪽에서는 VPC-SC 경계 규칙이 IAM 역할을 지원하게 됐다. 취약점을 찾고 고치는 에이전트 CodeMender에는 샌드박스 실행과 사람 확인 단계가 붙었다.

## 동작 원리
에이전트가 외부 시스템에 접속할 때 가장 흔한 방법은 장기 API 키를 환경 변수에 넣는 것이고, 그 키가 새면 끝이다. Agent Identity JWT는 키 대신 ‘이 에이전트가 누구인지’를 증명하는 단기 토큰을 클라우드가 발급하고, 상대 시스템이 그 토큰을 검증하게 한다. 복제할 수 있는 열쇠 대신 매번 발급되는 방문증으로 바꾸는 것이다. Auth Manager는 사용자 대신 받은 위임 토큰을 에이전트가 아닌 금고가 들고 갱신하게 해, 에이전트 프로세스에서 자격 증명을 떼어 낸다. VPC-SC의 IAM 역할 지원은 ‘어느 네트워크에서 왔나’뿐 아니라 ‘어떤 역할의 신원인가’로 데이터 경계를 긋는다. CodeMender의 변경은 공격 코드를 돌려 보는 에이전트를 격리 상자 안에 두고, 파일 쓰기·명령 실행 같은 되돌리기 어려운 행동 앞에 사람의 승인을 끼운다.

## 플랫폼 엔지니어 관점
- GKE·Cloud Run에서 도는 에이전트가 쓰는 외부 API 키·MCP 서버 토큰을 목록화하고, 워크로드 ID 연동과 단기 OIDC 토큰으로 바꿀 수 있는 것부터 옮긴다.
- 사내 MCP 서버가 외부 발급 OIDC 토큰을 받을 경우 audience·issuer·만료를 엄격히 검사하고, 다른 리소스용으로 발급된 토큰을 거부하는지 시험한다.
- 데이터가 있는 프로젝트에는 VPC-SC 경계를 두고, 수신·송신 규칙을 서비스 계정 단위가 아니라 역할 단위로 정리해 에이전트용 신원이 경계를 넘지 못하게 한다.
- 취약점 수정·레드팀 에이전트를 도입할 때는 익스플로잇 실행 환경을 프로덕션 자격 증명이 없는 격리 VM으로 분리하고, 저장소 쓰기·명령 실행에 승인 게이트를 둔다(공급사 기본값이 아니라 조직 정책으로). 프리뷰 기능은 GA 전에는 핵심 경로에 넣지 않는다.
