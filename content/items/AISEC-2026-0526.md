## 요약
화중과기대 Hou·Zhao·Wang·Wang의 이 논문은 MCP를 AI 모델과 외부 도구·자원을 잇는 개방 표준으로 보고, MCP 서버가 만들어져 배포되고 운영되다 갱신되는 생명주기 전체에서 어디가 뚫리는지 정리한 비전 논문이다. 최신판(v3, 2025-10-07)은 생명주기를 생성·배포·운영·유지보수 4단계 16개 활동으로 쪼개고, 공격자를 악의적 개발자·외부 공격자·악의적 사용자·보안 결함 4유형으로 나눠 위협 16개를 공격이 시작된 단계에 배정한다. 타이포스쿼팅·러그 풀·도구 오염·서버 간 섀도잉·명령 주입은 공식 SDK로 만든 개념 증명으로 재현했다. 완화책은 단계별로 서명된 매니페스트와 네임스페이스 관리, 서명·체크섬 검증 설치, 재현 가능 빌드와 버전 고정, 검증 가능한 중앙 레지스트리, 버전 관리된 구성과 롤백을 제시한다.

## 동작 원리
MCP 서버는 이름과 도구 설명이라는 '간판'을 내걸고, 호스트의 LLM은 그 간판을 읽고 어떤 서버·도구를 쓸지 고른다. 그래서 간판 단계에서 이미 공격이 시작된다. 이름을 비슷하게 짓거나(타이포스쿼팅), 같은 도구 이름을 등록하거나(도구 이름 충돌), 설명에 '나를 먼저 써라'는 문구를 넣으면(선호 조작) 모델이 가짜를 고른다. 배포 단계에서는 비공식 설치기가 다른 패키지를 끼워 넣을 수 있고(설치기 위장), 운영 단계에서는 처음엔 정상이던 서버가 나중에 행동을 바꾼다(러그 풀). 유지보수 단계의 위협은 악의가 아니라 관리 부재에서 온다. 중앙 감사가 없으니 오래된 취약 버전이 다시 깔리고, 핫 리로드 후에도 옛 자격 증명이 살아 있으며, 구성이 기준선에서 조금씩 멀어진다. 논문의 핵심 통찰은 공격이 심어지는 단계와 터지는 단계가 다르다는 것이다. 생성 때 심은 능력 선언이 운영 중 업데이트 이후에야 발동하므로, 한 시점의 검사만으로는 잡히지 않는다.

## 플랫폼 엔지니어 관점
- 사내 MCP 서버 허용 목록을 승인된 레지스트리로 운영한다. 서버 이름이 아니라 검증된 게시자 ID와 서명으로 식별하고, 이름이 비슷하거나 도구 이름이 겹치는 서버는 로드를 거부하도록 호스트·게이트웨이 정책에 넣는다.
- MCP 서버 패키지·컨테이너 이미지는 digest로 고정하고 서명 검증을 Kubernetes admission(예: Sigstore 정책 컨트롤러)이나 CI 단계에 둔다. 비공식 설치기의 자동 설치는 막고, 설치는 출처·버전·서명을 확인하는 파이프라인으로만 한다.
- 러그 풀에 대비해 버전이 바뀌면 도구 설명·스키마 diff를 자동으로 뽑아 재승인을 요구한다. 초기 승인만으로 신뢰를 고정하지 않는다.
- 서버 업데이트 시 해당 서버에 발급한 토큰을 회수·재발급하고, 토큰 만료를 서버 버전과 묶는다(업데이트 후 권한 잔존 대응, 9장 신원 통제와 연결).
- MCP 서버 구성은 GitOps로 버전 관리하고 기준 템플릿과의 드리프트를 지속 점검하며, 구 버전으로의 롤백·재배포가 취약 버전 재도입이 되지 않도록 최소 허용 버전을 정책으로 둔다.
