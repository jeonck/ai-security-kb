## 요약
OpenBMB의 멀티 에이전트 협업 플랫폼 IoA(Internet of Agents)에 새 CVE 두 건이 2026-11-06~07 게시됐다. 하나는 에이전트가 쓰는 코드 실행 도구 execute_code가 ‘Docker 컨테이너에서 실행한다’는 설명과 달리 샌드박스 없이 호스트에서 바로 python·bash·powershell을 돌리고, 파일 이름의 `../`를 걸러내지 않아 작업 폴더 밖에도 파일을 쓸 수 있다는 것이다(CVE-2026-123675). 다른 하나는 에이전트 레지스트리가 에이전트 이름을 데이터베이스 필터 문자열에 그대로 끼워 넣어, 이름 하나로 조회 논리를 바꾸고 다른 에이전트 정보를 읽을 수 있다는 것이다(CVE-2026-123791). 두 건 모두 10월 14일 이슈로 신고됐지만 유지보수자 응답이 없고 수정 버전도 없다. 앞서 게시된 같은 제품의 에이전트 사칭 결함(AISEC-2026-0497)과 같은 신고자다.

## 동작 원리
‘이 방의 실험은 모두 밀폐 상자 안에서 한다’는 안내문이 붙어 있지만 실제로는 상자가 없는 실험실이다. 에이전트가 코드를 실행하라는 요청을 받으면 도구는 그 코드를 에이전트 프로세스 권한으로 호스트에서 바로 돌린다. 요청을 넣는 쪽은 사람이 아니어도 된다. 같은 팀의 다른 에이전트(또는 이름만으로 그 자리를 사칭한 공격자)가 보낸 메시지가 피해 에이전트의 LLM을 움직여 도구를 호출하게 만들면 끝이다. 제공된 Docker 구성이 특권 모드와 Docker 소켓 마운트를 쓰기 때문에, 이 실행은 컨테이너 한 칸이 아니라 호스트 전체로 번질 수 있다. 레지스트리 쪽은 고전적인 쿼리 인젝션이다. 이름 안에 따옴표를 넣어 문자열을 일찍 닫고 `or key == ...` 같은 조건을 덧붙이면, 존재 확인이 항상 참이 되거나 남의 레코드가 돌아온다.

## 플랫폼 엔지니어 관점
- 에이전트 프레임워크를 도입할 때 ‘코드는 샌드박스에서 돈다’는 문서를 믿지 말고, 실제로 도구 안에서 `id`·호스트 이름·마운트 목록을 찍어 보는 검증을 도입 체크리스트에 넣는다.
- 코드 실행 도구는 별도 파드(gVisor·Kata 같은 강한 격리 런타임, 비루트, 읽기 전용 루트 파일 시스템, 기본 egress 차단, CPU·메모리·PID 제한)로 분리하고, 에이전트 컨테이너에 `privileged: true`나 `/var/run/docker.sock` 마운트를 두지 않는다. Pod Security Admission `restricted`와 Kyverno·Gatekeeper 정책으로 이를 강제한다.
- 멀티 에이전트 환경에서는 다른 에이전트가 보낸 메시지로 촉발된 고위험 도구 호출(셸·파일 쓰기)을 사람 승인 또는 정책 엔진 판정 뒤로 옮기고, 호출 로그에 ‘누가 시켰는가’를 남긴다.
- IoA처럼 수정이 없는 연구용 프레임워크는 내부망에서도 메시지 서버·레지스트리를 노출하지 말고 NetworkPolicy로 등록된 에이전트 파드만 접근하게 묶는다. 레지스트리 입력(에이전트 이름)에는 문자 허용 목록을 적용한다.
