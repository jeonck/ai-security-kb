## 요약
독일 웹호스팅 사업자 Mittwald는 고객이 자기 호스팅 관리 화면(mStudio)을 AI 비서와 연결하도록 MCP 서버를 운영해 왔다. 이 서버의 취약점으로 2026-10-27 무단 접근이 일어났는데, 회사는 11-04에야 자체 분석으로 알아챘다. 공격자는 MCP 사용자의 세션 토큰을 읽어 냈고, 그 토큰으로 사용자가 가진 권한 그대로 프로젝트에 접근할 수 있었다. Mittwald는 11-05 전 고객의 로그인·SSH·확장 기능을 끄고, 토큰을 모두 폐기한 뒤 프로젝트를 하나씩 스캔했다. mStudio는 11-07 복구됐지만 MCP 서버는 무기한 꺼져 있다. 기술적 근본 원인은 아직 공개되지 않았다.

## 동작 원리
MCP 서버는 AI 비서가 사용자 대신 호스팅 관리 기능을 호출하도록 돕는 중개자다. 일을 대신하려면 사용자의 세션 토큰을 들고 있어야 하므로, 서버는 많은 고객의 ‘대리 열쇠’를 모아 두는 보관함이 된다. 보관함 자물쇠(서버 취약점) 하나가 풀리자 열쇠 묶음이 통째로 나갔다. 탈취한 토큰은 정상 사용자의 권한 그대로 작동하므로, Mittwald 설명대로 공격자의 행동이 8일 동안 정상 사용과 구별되지 않았다. 프롬프트 인젝션이 아니라 전통적인 서버 결함이었다는 점도 중요하다. MCP의 위험은 모델이 아니라 연동 인프라와 그 토큰에서 온다.

## 플랫폼 엔지니어 관점
- 사내·고객용 원격 MCP 서버를 운영한다면 그 서버를 ‘토큰 금고’로 분류해 위협 모델·침투 테스트·패치 주기를 일반 API 게이트웨이 이상으로 둔다. 장기 세션 토큰 대신 짧은 수명·작업 범위로 좁힌 토큰을 발급하고(MCP 인가의 audience 바인딩·토큰 패스스루 금지), MCP 경유 토큰은 사람 세션 토큰과 분리한다.
- 탐지는 ‘토큰 주인이 맞나’보다 ‘이 토큰이 평소와 다른 출발지·도구·속도로 쓰이나’를 본다. MCP 경유 호출에 출처 IP·클라이언트 식별자·도구 이름을 남겨, 8일 동안 정상처럼 보이던 접근을 더 일찍 걸러 낸다.
- 사고 대응 런북에 ‘MCP 연동 토큰 일괄 폐기 → 연동 서비스 중단 → 프로젝트 단위 스캔 → 프로젝트에 저장된 외부 자격 증명 교체’ 순서를 미리 넣는다. 고객 쪽에서는 호스팅·SaaS MCP 연동을 켠 계정의 API 키·SSH 키·DB 비밀번호를 연동 해제 때 함께 교체하도록 안내한다.
