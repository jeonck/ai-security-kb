## 요약
AWS가 오픈소스로 운영하는 MCP 게이트웨이·레지스트리(mcp-gateway-registry)에 대해 2026-11-11 보안 공지 두 건이 동시에 나왔다. 하나는 서버 등록·수정 API가 업스트림 주소를 검증하지 않아 게이트웨이가 내부망 서비스로 요청을 대신 보내 주는 SSRF(CVE-2026-125926, CVSS 8.5, 1.35.0 수정)다. 다른 하나는 관리 API가 인증만 하고 인가를 하지 않아, 일반 사용자가 자기 그룹을 관리자 범위에 매핑해 레지스트리 관리자가 되는 권한 상승(CVE-2026-100307, CVSS 8.8, 1.25.0 수정)이다. 두 권고 모두 업그레이드가 과거에 저장된 악성 설정이나 이미 읽힌 자격 증명을 되돌리지 않는다고 강조하고, 사후 점검 절차를 따로 제시했다.

## 동작 원리
MCP 게이트웨이는 에이전트와 여러 MCP 서버 사이의 ‘교환대’다. 교환대에 새 회선(업스트림 주소)을 등록할 수 있는 사람이 메타데이터 주소나 사내 관리 콘솔 주소를 회선으로 등록하면, 교환대는 내부망 안쪽에서 그 주소로 전화를 걸고 응답까지 들려준다. 클라우드에서는 그 안쪽 주소 중 하나가 인스턴스 메타데이터 서비스라 게이트웨이 역할의 자격 증명이 새어 나갈 수 있다. 권한 상승 쪽은 출입증 검사(로그인)만 하고 출입 구역 검사(역할)를 빼먹은 경우다. 그룹-권한 매핑을 가져오는(import) API를 아무나 호출할 수 있었고, 관리자 판정이 요청마다 이 매핑을 읽어 계산되기 때문에 매핑을 바꾸는 즉시 관리자가 됐다. 두 결함을 합치면 일반 사용자 → 관리자 → 임의 서버 등록 → SSRF로 이어지는 연쇄가 가능하다.

## 플랫폼 엔지니어 관점
- mcp-gateway-registry를 쓰면 1.35.0 이상으로 올리고, 업그레이드 후 등록된 모든 서버·에이전트의 업스트림 URL을 목록화해 사설 대역·링크 로컬·클러스터 내부 DNS를 가리키는 항목을 찾는다. 관리자가 만들지 않은 그룹 매핑을 지운다.
- Kubernetes에서 게이트웨이 파드에 NetworkPolicy로 egress를 등록된 MCP 서버 대역과 IdP로만 제한하고, 노드 메타데이터 엔드포인트(169.254.169.254) 차단, EKS라면 IMDSv2 hop limit 1·IRSA/Pod Identity로 최소 권한 역할을 준다.
- 인그레스 계층에서 `/api/servers/*` 변경 라우트를 관리자 신원으로만 허용하는 이중 인가를 두고, 비관리자의 `POST /api/servers/groups/import` 호출을 탐지 규칙으로 건다.
- 레지스트리가 보관하던 백엔드 자격 증명은 영향 기간 로그가 불완전하면 교체한다. ‘MCP 게이트웨이 = 자격 증명 금고 + 프록시’라는 위협 모델로 다시 본다.
