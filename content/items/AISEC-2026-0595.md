## 요약
IBM이 오픈소스 MCP 게이트웨이 ContextForge의 보안 공지를 11월 12~13일에 여러 건 냈고, 11월 14일 GitHub 권고 DB에 8건이 한꺼번에 올라왔다. 가장 심각한 두 건은 신원 전파 서명이 정적이라 재생 가능했던 결함(CVE-2026-110278, 7.4)과, 요청 헤더 X-Upstream-Authorization 하나로 게이트웨이가 관리하는 업스트림 자격 증명을 바꿔치기할 수 있던 결함(CVE-2026-110279, 8.1)이다. 이 밖에 토큰 교환 캐시 키 혼동으로 권한 낮은 토큰이 높은 권한 토큰을 재사용하는 인가 우회, 팀 관리자가 다른 테넌트 도구의 엔드포인트를 덮어쓰는 가져오기 결함, SSRF가 있다. 수정 버전은 1.1.0(일부)과 1.1.1이다.

## 동작 원리
MCP 게이트웨이는 여러 사용자와 에이전트의 요청을 받아 뒤쪽 MCP 서버로 중계하며, 그때 ‘이 요청은 누구의 것인가’를 서명된 신원 클레임과 게이트웨이가 보관한 업스트림 자격 증명으로 증명한다. 이번 결함들은 그 증명의 연결 고리를 하나씩 끊는다. 서명이 매번 같으면 한 번 본 서명을 다시 붙여 다른 호출에도 쓸 수 있다. 클라이언트가 보낸 헤더가 게이트웨이의 자격 증명보다 우선하면, 사용자가 원하는 신원으로 업스트림을 부르고 감사 로그에는 엉뚱한 사람이 남는다. 토큰 교환 캐시의 키가 ‘계정’ 단위라 ‘어느 자격 증명으로 들어왔나’를 구분하지 못하면, 같은 계정의 제한된 API 토큰이 세션 토큰의 넓은 권한을 빌려 쓴다. 가져오기 기능이 기존 공유 객체의 소유자를 확인하지 않으면 한 팀 관리자가 다른 팀의 도구 주소를 공격자 서버로 바꿀 수 있다.

## 플랫폼 엔지니어 관점
- ContextForge를 쓰면 1.1.1 이상으로 올린다. 당장 못 올리면 앞단 Ingress·API 게이트웨이에서 X-Upstream-Authorization 헤더를 제거하는 규칙을 넣고, IDENTITY_PROPAGATION_ENABLED=false를 검토한다.
- 사내 MCP 게이트웨이(직접 만든 것 포함)에 대해 ‘클라이언트가 보낸 인증 관련 헤더가 게이트웨이 관리 자격 증명을 덮어쓸 수 있는가’, ‘토큰 교환 캐시 키에 인바운드 자격 증명 식별자가 들어가는가’를 점검 항목으로 둔다.
- 신원 전파 서명에는 호출별 nonce·만료·대상(aud, 게이트웨이 ID)을 넣어 재생과 다른 서버로의 전달을 막는다.
- admin.import 같은 대량 가져오기 권한은 플랫폼 관리자에게만 주고, 공유 도구의 엔드포인트 URL 변경은 감사 이벤트로 알림을 건다.
- 게이트웨이 감사 로그의 사용자 귀속이 이 기간 신뢰할 수 없었을 수 있으므로, 업스트림 측 로그와 대조해 이상 호출을 찾는다.
