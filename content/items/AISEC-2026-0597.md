## 요약
코딩 에이전트를 격리 실행하는 Docker Sandboxes의 취약점 2건이 11월 12일 NVD·GitHub 권고 DB에 등재됐다. 높은 쪽(CVE-2026-126329, 7.3)은 샌드박스 CLI(sbx)·데몬(sandboxd)이 기존 상태·설정 디렉터리의 소유자를 확인하지 않아, root로 실행되면서 HOME 경로가 공격자 영향 아래 있으면 로컬 사용자가 제어 소켓을 바꿔 root 권한 명령 실행까지 갈 수 있던 문제다. 낮은 쪽(CVE-2026-126330, 2.4)은 운영자가 지운 포트 매핑이 재시작 때 조용히 다시 열리던 문제다. 둘 다 0.53.0(11월 11일 릴리스)에서 고쳐졌다.

## 동작 원리
샌드박스 도구는 에이전트를 가두는 ‘우리’지만, 그 우리를 여닫는 열쇠는 호스트 쪽 데몬과 제어 소켓·설정 파일이다. 프로그램이 ‘내 상태 디렉터리’라고 믿는 경로가 실제로는 다른 사용자가 미리 만들어 둔 곳이면, 그 사용자가 넣어 둔 가짜 소켓·설정을 root 프로세스가 그대로 쓰게 된다. 우리 자체가 아니라 열쇠 보관함이 바뀐 것이다. 포트 재게시 문제는 ‘닫았다’는 운영자의 조치가 데몬의 내부 상태에는 반영되지 않아, 재시작이 곧 재개방이 되는 상태 불일치다.

## 플랫폼 엔지니어 관점
- Docker Sandboxes를 쓰는 개발자 단말·빌드 호스트를 0.53.0 이상으로 올린다(MDM·이미지 기준 버전 고정).
- sbx·sandboxd를 root로 돌리지 않는다. 불가피하면 sudo 환경 정리(env_reset)로 HOME·XDG_STATE_HOME이 호출자 값으로 넘어가지 않게 하고, 상태 디렉터리의 소유자·권한을 시작 시 검사한다.
- 공유 빌드 호스트처럼 여러 사용자가 있는 머신에서는 에이전트 샌드박스 데몬을 사용자별로 분리한다.
- 샌드박스 포트 게시는 재시작 후에도 실제 바인딩을 다시 점검(ss·lsof)하는 확인 단계를 둔다. 운영 조치가 데몬 상태에 반영됐는지가 감사 항목이다.
