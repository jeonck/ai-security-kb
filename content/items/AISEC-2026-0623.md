## 요약
Pulse는 호스트·노드를 감시하는 오픈소스 모니터링 도구로, AI 어시스턴트가 명령을 제안하고 사람이 승인하는 흐름을 갖고 있다(릴리스 노트는 어시스턴트가 명령을 실행하고 시스템 데이터를 읽는다고 설명한다). 이 승인 요청을 다루는 /api/ai/approvals 엔드포인트가 로그인 여부만 보고 ‘이 사용자가 승인할 자격이 있는가’를 보지 않았다. 그래서 조회 권한만 받은 사용자가 같은 조직의 대기 중인 명령과 대상 호스트를 읽고, 남의 요청을 승인하거나 거부할 수 있었다. 최종 실행 단계의 별도 검증 덕분에 실제 명령 실행으로는 이어지지 않았지만, 결정과 감사 기록이 엉뚱한 사람 이름으로 남을 수 있었다. 6.8.0(11월 13일)에서 고쳐졌고 CVE는 11월 14일 부여됐다.

## 동작 원리
승인 게이트는 ‘에이전트가 하려는 일’을 사람이 확인하는 문이다. 문 앞에서 출입증(로그인)은 검사했지만, 그 출입증에 ‘결재권’이 찍혀 있는지는 보지 않은 셈이다. 원인은 권한 검사 함수가 API 토큰 전용으로 짜여 있어, 토큰이 없는 브라우저 세션 요청은 통과시키던 데 있다. 같은 제품 안에서도 액션 결정 경로는 승인 권한을 제대로 확인했는데, AI 승인 경로만 다른 코드 길을 타면서 검사가 빠졌다. 실행 직전 검증기가 실행 계획과 액션 ID를 다시 맞춰 보는 두 번째 방어선이 있었기 때문에 피해가 상태 변경에 그쳤다.

## 플랫폼 엔지니어 관점
- 에이전트 승인 기능을 둔 내부 도구·운영 콘솔에서 ‘승인 목록 조회’와 ‘승인·거부’가 각각 어떤 역할로 제한되는지, 세션·API 토큰·SSO 프록시 사용자 경로마다 따로 확인한다. 토큰 범위 검사만으로 세션 사용자를 걸러낼 수 있다고 가정하지 않는다.
- 승인 요청 기록에는 명령·대상 호스트가 담기므로 그 자체가 민감 정보다. 조회 권한 분리, 감사 로그에 결정자 역할까지 남기기를 기본으로 한다.
- 승인과 실행을 분리하고, 실행 직전에 승인된 실행 계획·ID와 실제 명령을 다시 대조하는 두 번째 검증을 둔다. 이번 사례에서 피해를 막은 것이 바로 이 층이다.
- Pulse를 쓰는 팀은 6.8.0 이상으로 올리고, 업그레이드 전에는 승인 요청을 봐도 되는 사람에게만 viewer 권한을 준다.
