## 요약
Jupyter 노트북을 AI 어시스턴트가 직접 읽고 쓰게 해 주는 Datalayer의 jupyter-mcp-server에서, 노트북 백엔드를 바꾸고 커널을 멈추는 관리용 HTTP 경로 두 개가 인증과 Host/Origin 검사를 받지 않았다. 악성 웹페이지는 DNS 리바인딩으로 사용자의 로컬 서버에 요청을 보내 백엔드를 공격자 Jupyter로 바꿀 수 있었고, 어시스턴트는 그 사실을 모른 채 계속 같은 MCP 연결을 썼다. Pluto Security는 이 방법으로 기밀 노트북 내용을 공격자 쪽에 저장시키거나, 조작된 수치를 진짜 노트북에 옮겨 적게 만드는 시나리오를 보였다. 수정은 7월 1.0.3에서 나왔고 연구 글은 8월에 공개됐으며, 11월 19~20일 CVE가 NVD와 GitHub Advisory Database에 올라왔다.

## 동작 원리
정문(/mcp)에는 경비원이 서서 출입증과 방문자 주소를 확인했지만, 바로 옆 관리용 쪽문(/api/connect)에는 아무도 없었다. 브라우저는 DNS 리바인딩으로 ‘공격자 사이트’라는 이름표를 단 채 실제로는 사용자의 127.0.0.1에 요청을 보낼 수 있다. 그 요청이 쪽문으로 들어가 ‘앞으로 노트북은 이 서버에서 가져와라’라고 설정을 바꾸면, 에이전트는 평소처럼 도구를 호출하지만 읽고 쓰는 노트북은 모두 공격자 것이 된다. 모델을 속이는 인젝션이 아니라 모델이 믿는 배관을 바꿔 끼우는 공격이라, 모델 쪽 방어로는 보이지 않는다.

## 플랫폼 엔지니어 관점
- 개발자 PC·노트북 서버에서 jupyter-mcp-server를 HTTP 모드로 쓰는 곳을 찾아 1.0.3 이상으로 올리고, 가능하면 stdio로 바꾼다. HTTP가 필요하면 127.0.0.1 바인딩과 명시적 허용 호스트 목록을 강제한다.
- 사내 MCP 서버 리뷰 체크리스트에 ‘SDK 전송 계층 밖에서 추가한 custom route도 같은 인증·Origin 미들웨어를 타는가’를 넣는다. FastMCP 등에서 custom_route를 쓰는 서버는 별도로 점검한다.
- 공유 JupyterHub·쿠버네티스 위 노트북 환경에 MCP 브리지를 붙일 때는 MCP 서버가 쥐는 Jupyter 토큰을 사용자별·단기로 발급하고, MCP 서버의 egress를 승인된 Jupyter 엔드포인트로만 허용해 ‘백엔드 바꿔치기’가 일어나도 외부로 연결되지 않게 한다.
- 탐지: MCP 서버 로그에서 /api/connect 호출과 백엔드 URL 변경을 경보 대상으로 삼는다.
