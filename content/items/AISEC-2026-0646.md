## 요약
할 일 관리 서비스 Todoist를 만드는 Doist의 공식 MCP 서버에서, 선택 기능인 HTTP 서버가 브라우저에서 온 요청의 Host·Origin을 확인하지 않았다. 서버는 127.0.0.1에만 묶여 있었지만, 사용자가 악성 웹사이트를 방문하면 DNS 리바인딩으로 그 페이지가 로컬 서버에 MCP 요청을 보낼 수 있었다. 서버는 호출자가 누구인지 묻지 않고 운영자가 설정한 Todoist API 키로 모든 도구를 실행했기 때문에, 공격자는 계정 정보를 읽고 작업을 만들고 완료하고 지울 수 있었다. 10.3.3에서 수정됐고 11월 18~19일 CVE-2026-76807로 NVD와 GitHub Advisory Database에 올라왔다.

## 동작 원리
‘집 안에서만 들리는 인터폰’이라 안심했는데, 손님(웹페이지)이 집 안의 브라우저를 통해 그 인터폰을 누를 수 있었던 셈이다. DNS 리바인딩은 공격자 도메인의 주소를 처음엔 공격자 서버로, 다음엔 127.0.0.1로 바꿔 주어 브라우저의 동일 출처 정책을 피해 간다. 여기에 서버의 토큰 검사가 ‘서버에 키가 설정돼 있나’만 보고 ‘요청한 사람이 키를 가졌나’를 보지 않았으니, 운영자의 키가 아무 웹페이지에게나 빌려준 열쇠가 됐다.

## 플랫폼 엔지니어 관점
- 개발자 단말 관리(MDM·엔드포인트 인벤토리)로 로컬에서 HTTP 모드로 도는 MCP 서버(todoist-mcp-http 등)를 찾고, 기본은 stdio를 쓰도록 사내 가이드를 정한다.
- 사내에서 만드는 로컬·원격 MCP 서버의 공통 템플릿에 Host 허용 목록, Origin 거부, 실행마다 생성되는 로컬 bearer 토큰을 기본으로 넣는다. SDK의 DNS 리바인딩 보호 옵션이 켜져 있는지 확인한다.
- MCP 서버에 주는 SaaS API 키는 쓰기 범위를 최소로 하고, 서버가 쥔 키로 ‘누구의 요청이든’ 실행하는 구조를 리뷰에서 금지한다. 가능하면 사용자별 OAuth 위임으로 바꾼다.
- 브라우저 정책(사설 네트워크 접근 제한)을 사내 브라우저 관리 정책으로 강제해 공개 웹페이지가 루프백·사설 주소로 요청하지 못하게 한다.
