## 요약
MISP와 연동하는 조사·사건 관리 플랫폼 FlowIntel의 챗봇에서 사용자 신원이 섞이는 결함(CVE-2026-133853)이 11월 20일 NVD·GitHub 권고 DB에 올라왔다. 챗봇은 MCP 클라이언트 세션 하나를 모든 요청이 함께 썼고, 요청한 사용자의 API 키를 프로세스 전역 환경 변수에 써 넣은 뒤 MCP 서버 자식 프로세스에 넘겼다. 두 사용자의 도구 호출이 겹치면 저권한 사용자의 요청이 고권한 사용자 키로 실행될 수 있었고, 폐기된 키도 환경 변수에 남아 계속 쓰일 수 있었다. 같은 날 앞서 공개된 CVE-2026-133631은 챗봇 API 도구에 허용 목록이 없어 사례 본문 같은 신뢰할 수 없는 입력으로 모델을 조종하면 관리자·상태 변경 API까지 부를 수 있었다고 적었다. 두 결함 모두 수정 커밋이 있으나 수정판(4.1.0) 릴리스는 확인하지 못했다.

## 동작 원리
은행 창구 하나에 직원 한 명이 앉아 있고, 손님이 올 때마다 그 손님의 도장을 책상 위 공용 도장함에 넣어 두는 구조라고 생각하면 된다. 직원은 업무를 볼 때 도장함에 지금 들어 있는 도장을 집는데, 손님 두 명이 거의 동시에 오면 앞 손님의 도장으로 뒤 손님 업무를 처리하게 된다. 여기서 직원이 공유 MCP 세션, 도장함이 `FLOWINTEL_API_KEY` 환경 변수다. 수정 커밋은 손님마다 창구를 새로 열고 그 창구에만 도장을 건네는 방식, 즉 도구 호출마다 MCP 세션과 자식 프로세스를 새로 띄우고 키를 그 자식 환경에만 넣는 방식으로 바꿨다.

두 번째 CVE는 권한 범위 문제다. 모델이 쓰는 ‘API 호출’ 도구가 경로 제한 없이 플랫폼 API 전체를 부를 수 있었다. 사례 본문에 숨긴 지시가 모델을 움직이면 그 호출은 사용자의 권한으로 관리 경로까지 간다. 수정은 읽기·검색만 기본 허용하고 쓰기는 별도 설정을 켜야만 열리게 했다.

## 플랫폼 엔지니어 관점
- 사내 에이전트·챗봇이 MCP 서버를 stdio 자식 프로세스로 띄운다면, 자격 증명을 `os.environ` 같은 프로세스 전역 상태로 넘기는 코드가 있는지 점검한다. 멀티유저 서비스라면 요청마다 세션과 자격 증명을 분리하고, 요청 신원을 서버 측 세션에서 다시 확인한 뒤에만 도구를 실행하게 한다.
- 동시성 테스트를 보안 테스트에 넣는다. 서로 다른 권한의 두 사용자가 동시에 도구를 호출할 때 감사 로그의 행위자가 실제 요청자와 같은지 확인하는 회귀 테스트가 필요하다.
- ‘범용 API 호출’ 도구는 기본 거부로 두고 읽기 엔드포인트 허용 목록부터 시작한다. 쓰기는 별도 플래그·사람 승인 뒤로 둔다. 자격 증명은 명령행 인자로 넘기지 않는다(`ps`로 보인다). 표준 입력이나 파일 디스크립터로 넘긴다.
- FlowIntel을 쓰는 SOC·CERT 팀은 4.1.0 릴리스나 해당 커밋을 반영하기 전까지 챗봇 기능을 끄는 방안을 검토한다(3.2.0부터 시스템 설정에서 켜고 끌 수 있다).
