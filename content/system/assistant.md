## 왜 이렇게 나눴나

- **코디네이터는 검색하지 않는다.** 한 에이전트가 검색·판단·기록을 다 하면 컨텍스트가 검색 결과로 가득 차 판단이 흐려진다. 리서처는 노트 파일만 남기고, 코디네이터는 노트를 읽어 중복 제거·선별·기록만 한다.
- **도메인 4개는 서로 겹치지 않게** 잘랐다(인젝션·에이전트 / 모델 공격 연구 / 공급망·데이터·악용 / 규제·표준·벤더). 같은 사건을 두 리서처가 가져오면 코디네이터가 하나로 합친다.
- **리서처에게 이미 수집한 항목 목록을 넘긴다.** 이미 실린 기사를 다시 찾느라 쓰는 시간을 줄이기 위해서다.
- **리서처가 완성된 항목 파일을 써 온다(v4).** 1차 원문까지 열어 출처 메타데이터와 주장별 위치를 채우는 일은 원문을 읽은 리서처가 가장 정확하게 할 수 있다. 코디네이터는 중복 판정·축 태그 점검·ID 부여·다이제스트·검증·커밋을 맡는다.

## 1. 병렬 수집 (리서처 4명)
Agent 도구(subagent_type="general-purpose", run_in_background=false)로 아래 4명을 **한 번의 메시지에서 동시에** 띄운다. 너는 직접 검색하지 않는다. 각 리서처 프롬프트에 다음을 모두 넣는다:
- 담당 도메인과 세부 주제(아래), 기간 "<last_run> 이후 발행된 것만"(명시적 날짜로), 기존 항목 목록(ID·제목·URL)과 그 도메인의 후속 추적 항목
- `docs/item-format.md`와 `data/axes.yaml`의 절대 경로를 주고 먼저 읽게 한다
- 방법: WebSearch(standard 기본, 빈약하면 extended)로 세부 주제마다 **따로** 검색하고, 후보는 반드시 WebFetch로 원문을 연다. **기사가 원 보고서·보안 권고·논문·공식 발표에 링크하면 그 1차 원문까지 열어** 발행일·수치·버전을 1차 원문 기준으로 확인한다. 검색어에 현재 연·월 포함.
- 웹 접근 규칙: WebFetch가 거절(429 요청 제한, 차단, 법적 사유)하면 재시도하거나 curl·스크립트·캐시·미러·아카이브·브라우저 위장 등으로 우회하지 않는다(arXiv는 abs가 막히면 같은 사이트의 html/<id>v1 정식 페이지를 한 번 시도하는 것까지만 허용). 다른 공개 출처로 교차 확인하고, 안 되면 status를 낮춘다. 사실·수치·링크는 실제로 읽은 페이지에서 나온 것만. 원문 문장을 옮기지 않는다.
- 출력: 후보마다 `docs/item-format.md` 형식의 완성된 항목 파일을 `<작업 폴더>/<도메인>/cand-<n>.md` 로 쓴다(id는 "TBD"로 비워 둔다, collected는 이번 실행 시각). 영향도 순, 도메인당 최대 6개. 없으면 "없음". 최종 답변은 후보 파일 목록과 각 후보의 1차 원문 URL·status 한 줄씩만.

리서처 도메인:
1. **인젝션·에이전트** — 직접/간접 프롬프트 인젝션, 데이터 유출 체인, 브라우저·이메일·코딩 에이전트, MCP 서버/SDK, 에이전트 신원·권한, 관련 GHSA/CVE
2. **모델 공격 연구** — 탈옥, 적대적 예제, 백도어·데이터 포이즈닝, 모델 추출·증류, 정렬 우회, 멤버십 추론·학습 데이터 추출 (arXiv cs.CR·cs.LG·cs.CL 신규 논문, 주요 연구소 블로그)

## 2. 검증·선별 (코디네이터)
- 후보 파일을 모두 읽는다. 각 후보의 1차 URL·제목 키워드·CVE/GHSA/arXiv ID로 `python3 scripts/kb.py find <...>` 를 돌려 기존 항목과 겹치면 제외한다(중요한 후속은 "후속: …" 새 항목 + related, 원 항목 followup 정리). 리서처끼리 겹치면 하나로 합치고 출처 병합.
- 기간 밖, 1차 출처도 2등급 출처도 없는 후보, claims의 locator가 비어 있는 후보는 버린다. 영향도 순 최대 12개.
- 두 축 태그를 다시 본다: 생명주기는 사건의 중심 단계, 통제는 "이 사례가 어떤 통제의 실패/필요성을 보여주나". 거버넌스만 달린 항목에는 구체 통제를 추가한다. book_note는 outline.md의 장 번호·제목에 맞춘다.
- **심층 후보 판정**: 남은 후보 중 CLAUDE.md·docs/item-format.md의 기준(실제 악용 확인 / 영향 범위가 큼 / 새 공격 유형 / 책의 장을 바꿀 만함)에 맞는 것에만 `deep_dive: true`와 `deep_dive_reason`(기준 + 이유 한 줄)을 단다. 보통 0~2건. 기존 항목의 후속(예: KEV 등재로 실제 악용 확인)이 기준을 새로 충족하면 원 항목에 표시를 단다.

## 버전 변경 이력

| 버전 | 시각 (2026-10-20 CT) | 구조 | 기록 위치 | 계기 |
|---|---|---|---|---|
| v1 | 07:19 | 단일 에이전트가 직접 검색·요약·기록 | claude.ai 프로젝트 | 최초 요청 |
| v2 | 07:22 | 코디네이터 + 병렬 리서처 4명 | claude.ai 프로젝트 | deep-research 방식 제안 |
| v3 | 07:32 | v2 + 레포 커밋·`check.sh`·대체 모드 | GitHub 레포(원본) + 프로젝트(사본) | GitHub 버전 관리 제안 |

**v1에서 v4까지 바뀌지 않은 것**: 날짜를 명령 출력으로 정하는 규칙, 원문 확인 원칙, 차단 시 우회 금지, 새 자료 0건이면 아무것도 쓰지 않는 규칙, 실행당 최대 12건, 보고 첫 줄 형식.

**v1 → v2**: 1단계 "수집"이 코디네이터가 직접 검색하던 방식에서, 리서처 4명을 한 번에 띄우고 노트 파일로 결과를 받는 방식으로 바뀌었다. 코디네이터에게 "너는 직접 검색하지 않는다"가 추가됐다.

**v2 → v3**: 규칙의 원본이 프로젝트 `ai-security/README.md`에서 레포 `CLAUDE.md`로, 이력의 원본이 `ai-security/index.md`에서 `content/catalog.md`로 옮겨졌다. 기록 단계에 `check.sh` 통과·커밋·푸시·프로젝트 사본 갱신이 추가됐고, 레포 접근 실패 시 대체 모드가 생겼다.

**v3 → v4**: 기록 단위가 "다이제스트 안의 문단"에서 "항목 파일 하나"로 바뀌었다. 리서처의 출력이 노트에서 완성된 항목 파일로, 중복 판정이 catalog 표의 URL 대조에서 `kb.py find`로, 이력 기록이 catalog 머리말에서 `data/state.yaml`로 옮겨졌다. 레포 접근 실패 시 프로젝트 대체 모드는 없앴다(항목 체계가 레포에만 있기 때문).

**v4 → v4.1** (11:20경): 코디네이터가 기준(실제 악용 확인 / 영향 범위가 큼 / 새 공격 유형 / 책의 장을 바꿀 만함)에 맞는 항목에 **심층 후보** 표시(`deep_dive`)를 단다. 표시된 항목은 다음 주간 리포트가 딥 리서치로 파고든다.
